# SABA TESTING RULES

Version: 1.1


==================================================
CRITICAL TESTING RULE
==================================================

A feature or behavior change MUST NOT be reported as complete
until all tests required by the approved scope have been
executed and passed.

Do NOT weaken, delete, skip, bypass, or rewrite an existing
requirement or test merely to make an implementation pass.

Mock or fixture success MUST NOT be reported as a successful
real-world external connection.

A previous test result MUST NOT be presented as the result of
the current implementation.

Tests MUST NOT modify or destroy user production data.

Secrets MUST NOT appear in source code, fixtures, logs, test
output, or error messages.

All model-authored user-facing natural-language explanations,
progress messages, and test reports MUST be written in Korean
and MUST NOT contain CJK ideographs.


==================================================
1. 목적
==================================================

이 문서는 SABA 프로젝트의
구현 및 변경 작업에 적용하는
공통 테스트 규칙을 정의한다.

다음 작업에 적용한다.

- 기능 구현
- 기능 변경
- 버그 수정
- CLI 변경
- Schema 변경
- Storage 변경
- Collector 변경
- AI 관련 구현
- Template 변경
- Mail 변경
- Scheduler 변경
- Admin UI 변경
- 운영 설정 변경

기능 구현과 테스트를
별개의 선택 작업으로 취급하지 않는다.


==================================================
2. 작업 시작 전 확인
==================================================

구현 또는 변경 작업 전에 최소 다음을 확인한다.

- PROJECT_RULES.md
- DEVELOPMENT_STATUS.md
- harness/ 아래의 모든 규칙 파일
- 현재 작업 경로에 적용되는 AGENTS.md
- 기존 Source Code
- 기존 Test
- 기존 Fixture
- Git 상태

현재 구현과 테스트 구조를 확인하지 않고
불필요하게 새 테스트 구조를 만들지 않는다.


==================================================
3. 기본 원칙
==================================================

1. 필요한 테스트 없이 기능 완료를 선언하지 않는다.

2. 새 기능 또는 변경된 동작에는
   해당 동작을 직접 검증하는 테스트를 작성한다.

3. 변경 후 기존 전체 테스트를 실행하여
   회귀 문제가 없는지 확인한다.

4. 테스트를 통과시키기 위해
   요구사항이나 기존 테스트를
   임의로 약화하지 않는다.

5. 실패가 발생하면
   실패 사실과 영향을 보고한다.

6. Mock과 Fixture 검증 결과를
   실제 외부 연결 성공으로 표현하지 않는다.

7. 테스트에서 사용자 운영 DB 또는
   실제 전체 직원 메일 발송을 사용하지 않는다.

8. Secret을 Fixture, Source Code,
   로그 또는 오류 메시지에 포함하지 않는다.

9. 오류 출력에 인증정보,
   전체 외부 Response,
   전체 기사 데이터 등이
   불필요하게 노출되지 않는지 확인한다.


==================================================
4. 테스트 작성 기준
==================================================

새로운 동작을 구현하거나
기존 동작을 변경하면
가능한 범위에서 다음을 검토한다.

- 정상 입력
- 잘못된 입력
- 빈 입력
- 경계값
- 중복
- 실패 처리
- 재실행
- 기존 데이터 보존
- 외부 의존성 실패
- Network 미사용 경로
- 사용자 데이터 영향

모든 항목을 기계적으로
테스트해야 한다는 의미는 아니다.

현재 변경과 직접 관련된 항목을
선택하여 검증한다.


==================================================
5. 회귀 테스트
==================================================

변경된 기능의 직접 테스트가 통과해도
작업을 완료로 처리하지 않는다.

기존 전체 테스트를 실행하여
다른 기능이 깨지지 않았는지 확인한다.

과거의 테스트 개수를
현재 테스트 개수로 사용하지 않는다.

현재 실행 결과를 기준으로 보고한다.


==================================================
6. 테스트 삭제 및 변경
==================================================

기존 테스트가 실패한다는 이유만으로
테스트를 삭제하거나 약화하지 않는다.

기존 테스트가 현재 승인된 요구사항과
실제로 충돌한다고 판단되는 경우:

- 기존 요구사항
- 현재 요구사항
- 충돌하는 테스트
- 변경 필요 이유
- 영향

을 확인한다.

사용자 결정이 필요한 경우
임의 변경하지 않는다.


==================================================
7. Mock 및 Fixture
==================================================

Mock과 Fixture는
외부 의존성 없이 내부 동작을
검증하기 위한 수단이다.

Mock 성공은
실제 API 연결 성공이 아니다.

Fixture 성공은
실제 뉴스 품질 검증이 아니다.

결과 보고에서 이를 명확하게 구분한다.


==================================================
8. 외부 연결 테스트
==================================================

실제 외부 연결은
해당 단계에서 승인된 경우에만 수행한다.

예:

- 실제 RSS 요청
- 실제 API 요청
- 실제 AI API 요청
- 실제 Mail TEST 발송

실제 연결이 승인되지 않았다면
Mock 또는 Fixture 검증 범위까지만 수행한다.

승인되지 않은 외부 요청을
테스트라는 이유로 실행하지 않는다.


==================================================
9. 데이터베이스 테스트
==================================================

테스트에서는 가능한 범위에서:

- 임시 DB
- 임시 디렉터리
- 테스트 전용 데이터

를 사용한다.

사용자 실제 DB를
테스트 목적으로 초기화하거나 삭제하지 않는다.

기존 사용자 데이터가 존재한다면
보존을 우선한다.


==================================================
10. Mail 테스트
==================================================

Mail 기능 테스트 시
실제 전체 직원 배포를 수행하지 않는다.

실제 발송 테스트가 승인된 경우에도
승인된 TEST 수신자만 사용한다.

운영 수신자 목록과
TEST 수신자를 구분한다.


==================================================
11. AI 테스트
==================================================

AI 기능이 구현되는 경우
harness/AI_RULES.md를 함께 적용한다.

가능한 범위에서 다음 경로를 구분한다.

1. AI 사용 경로
2. AI 미사용 경로
3. AI 실패 경로

AI 미사용 경로에서는
외부 AI Network 요청이 없어야 한다.

AI 장애가
Core Pipeline 전체 실패로
불필요하게 전파되지 않는지 확인한다.

실제 AI API 테스트는
Provider, Model, 비용 및 실제 호출이
승인된 경우에만 수행한다.


==================================================
12. 보호 파일
==================================================

PROJECT_RULES.md에서 정의한
보호 파일을 테스트 과정에서 변경하지 않는다.

필요한 경우 작업 전후:

- 파일 목록
- SHA-256

을 비교한다.

테스트 편의를 위해
보호 원본을 수정하지 않는다.


==================================================
13. 테스트 실행 순서
==================================================

기능 구현 또는 변경 시
기본 순서는 다음과 같다.

요구사항 확인
→ 영향 범위 확인
→ 테스트 사례 결정
→ 구현
→ 직접 관련 테스트
→ 실패 및 경계 조건 테스트
→ 전체 회귀 테스트
→ 필요한 경우 승인된 실제 연결 검증
→ 결과 보고
→ 사용자 확인


현재 작업 특성상
순서를 일부 조정할 수는 있지만
필수 검증을 생략해서는 안 된다.


==================================================
14. 테스트 결과 보고
==================================================

가능한 경우 다음을 보고한다.

- 실행한 명령
- 실행된 테스트 개수
- 성공 개수
- 실패 개수
- Skip 개수
- 종료 코드
- 실제 외부 연결 여부
- 사용자 DB 영향
- 보호 파일 영향

과거 결과가 아니라
현재 실제 실행 결과를 사용한다.


==================================================
15. 실패 처리
==================================================

필수 테스트가 실패하면
작업을 완료로 표시하지 않는다.

실패 시 다음을 확인한다.

- 실패 테스트
- 원인
- 변경 영향
- 기존 기능 영향
- 해결 가능한 범위
- 사용자 결정 필요 여부

사용자 결정 없이
요구사항이나 테스트를 약화하지 않는다.


==================================================
16. 완료 조건
==================================================

테스트가 필요한 구현 작업은
최소 다음을 만족해야 완료로 처리할 수 있다.

- 요구사항에 필요한 구현 완료
- 직접 관련 테스트 완료
- 필요한 실패 및 경계 테스트 완료
- 전체 회귀 테스트 완료
- 필수 테스트 통과
- 보호 대상 이상 없음
- 사용자 데이터 손상 없음

실제 외부 연결이
현재 단계 완료 조건에 포함된 경우에는
해당 검증도 완료되어야 한다.


==================================================
17. 규칙 변경
==================================================

테스트 통과를 위해
이 규칙을 임의로 약화하지 않는다.

변경이 필요한 경우:

- 변경 이유
- 기존 규칙
- 변경안
- 영향

을 사용자에게 보고한다.

사용자의 최신 명시적 결정과
이 문서가 충돌하면
최신 사용자 결정을 우선하고
필요한 문서 갱신을 보고한다.
