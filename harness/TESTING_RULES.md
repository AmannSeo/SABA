# SABA TESTING RULES

## 목적
SABA에서 기능 또는 코드를 추가·수정할 때마다 해당 변경을 검증하는 테스트를 함께 설계·작성·실행하도록 한다.

적용 대상: 기능 구현, 버그 수정, CLI, Schema, Storage, Collector, AI, Template, Mail, Scheduler, Admin UI, 운영 설정.

작업 시작 전 `PROJECT_RULES.md`, `DEVELOPMENT_STATUS.md`와 함께 반드시 확인한다.

## 기본 원칙
1. 기능 코드만 작성하고 테스트 없이 완료 처리하지 않는다.
2. 새 기능/동작 변경에는 해당 동작을 직접 검증하는 테스트를 추가한다.
3. 변경 후 기존 전체 테스트를 실행해 회귀를 확인한다.
4. 테스트 통과를 위해 요구사항이나 기존 테스트를 임의로 약화·삭제·skip하지 않는다.
5. 실패 시 원인과 영향 범위를 보고한다.
6. Mock/Fixture 성공과 실제 외부 연결 성공을 구분한다.
7. 사용자 DB·운영 DB·전 직원 메일을 테스트 대상으로 사용하지 않는다.
8. Secret을 Fixture·로그·소스에 넣지 않는다.
9. 오류 로그에 인증정보, 응답 본문 전체, 기사 JSON 전체가 노출되지 않는지 확인한다.

## 구현 단계의 필수 순서
요구사항 확인 → 영향 범위 확인 → 테스트 항목 정의 → 기능 코드 작성/수정 → 단위 테스트 → 실패/경계 테스트 → 전체 회귀 테스트 → 필요한 실제 연결 검증 → 결과 보고 → 사용자 확인

가능하면 기능 구현과 같은 단계에서 테스트 코드를 작성한다.

## 테스트 종류
- 단위 테스트: Schema, 파싱, 변환, 순수 규칙 등.
- 통합 테스트: 여러 모듈의 연결을 임시 DB·Fixture·Mock으로 검증.
- 회귀 테스트: 기존 전체 테스트 재실행.
- 실제 연결 검증: RSS/API/AI/Mail 등은 Mock과 별도로 최소 요청으로 확인. 승인되지 않은 단계에서는 실행하지 않는다.

## 공통 검증 관점
해당되는 항목을 확인한다.
- 정상 입력/동작
- 빈 값/누락 값/잘못된 타입
- 최소·최대·시간 경계
- 중복 및 재실행
- Timeout/네트워크 실패/잘못된 외부 응답
- 인증·권한 실패
- 파일/DB 오류
- 기존 데이터 보존
- Transaction/Rollback
- CLI 옵션 충돌
- 예상하지 못한 입력
- Secret/원문 로그 노출
- 종료 코드
- 기존 기능 회귀

## 영역별 최소 검증
### RSS / API / Crawling
정상 파싱, 필수 필드, Article Schema, 안정적 ID, 날짜/시간대, 응답 크기, Timeout, HTTP 오류, 예상 밖 형식, 정상 0건, 재수집 정책, 실제 요청 수, Mock/실제 결과 구분.

### SQLite / Storage
최초 저장, 재저장, 중복, 충돌, Transaction/Rollback, 별도 연결 재조회, 기존 시간/데이터 보존, 사용자 DB 미사용.

### AI
입력/출력 Schema, 허용·금지 필드, JSON 오류, 입력 부족, 근거 연결, 환각 방지 규칙, Timeout/API 오류/Rate Limit, 잘못된 응답, 재시도 정책, 호출 수/비용, Mock/실제 결과 구분. 실제 분석 품질은 사람 검토도 포함한다.

### Newsletter / Template
승인된 최신 디자인 확인, 보호 원본 Hash 불변, 필수 영역, 동적 데이터 Escape, 누락 데이터, 긴 텍스트, 0건 섹션, 회사 서명, 이메일 HTML 호환성. 샘플 데이터를 운영 규칙으로 사용하지 않는다.

### Mail
기본 TEST 모드, 테스트 수신자 제한, Production 오발송 방지, 제목/본문/서명, HTML, 인증 실패, 서버 거부, Timeout, 중복 발송 정책, 발송 요청 성공과 실제 전달 성공 구분, Secret 로그 미노출. 전 직원 발송은 명시적 승인 전 금지.

### Scheduler
지정 시각/시간대, ON/OFF, 시간 변경, 중복 실행 방지, 실패 처리, 서버 재시작 후 설정, 수동/자동 실행 충돌, 사용자 PC와 독립된 서버 실행 구조.

### Admin UI
설정 조회/저장, 자동 실행 ON/OFF, TEST/PRODUCTION 표시, 발송 시간, 테스트 수신자 제한, 수동 실행, 테스트 메일, Preview, 로그, 잘못된 입력, 위험 작업 확인 절차. 인증/접근 통제는 배포 환경 확정 시 별도 검증한다.

## Fixture / Mock 규칙
- 합성 데이터를 우선 사용한다.
- 실제 사건·개인정보·Secret을 Fixture에 넣지 않는다.
- 최소 데이터로 목적을 명확히 한다.
- 성공뿐 아니라 오류·Timeout·잘못된 응답을 포함한다.
- Mock 성공을 실제 서비스 성공으로 보고하지 않는다.

## 테스트 파일 원칙
기능과 대응 테스트를 명확하게 유지한다.
- `src/saba/rss.py` → `tests/test_rss.py`
- `src/saba/storage.py` → `tests/test_storage.py`
- `src/saba/analysis.py` → `tests/test_analysis.py`

새 모듈에는 특별한 이유가 없는 한 같은 단계에서 대응 테스트를 만든다. 기존 `unittest`를 우선 재사용한다.

## 결과 보고
각 구현 단계 종료 시 최소 다음을 보고한다.
- 구현/변경 기능
- 생성/수정 파일
- 추가 테스트와 검증 항목
- 실행 명령
- 신규 테스트 결과
- 전체 회귀 테스트 결과
- 실제 연결 검증 여부
- 성공/실패/보류
- 종료 코드
- 사용자 데이터/DB 영향
- 보호 파일 Hash 결과
- 알려진 제한사항
- 다음 단계 진행 가능 여부

테스트 개수뿐 아니라 무엇을 검증했는지도 보고한다.

## 실패 시
필수 테스트 실패 시 단계 완료로 처리하지 않는다. 다음 단계로 넘어가지 않고 실패 원인, 영향 범위, 승인 범위 안의 수정안, 재검증 방법을 보고한다. 승인 범위 밖 수정은 사용자에게 확인한다.

## 모든 향후 구현 프롬프트에 포함할 지시
“작업 시작 전 PROJECT_RULES.md, DEVELOPMENT_STATUS.md, TESTING_RULES.md와 적용되는 AGENTS.md를 읽는다. 이번 변경에 해당하는 테스트를 기능 코드와 함께 작성·실행한다. 신규 테스트뿐 아니라 기존 전체 테스트를 실행하여 회귀를 확인한다. Mock/Fixture 테스트와 실제 외부 연결 검증을 구분한다. 필수 테스트 실패를 숨기거나 테스트를 약화해 통과시키지 않는다. 결과 보고 후 사용자 승인 없이 다음 단계로 넘어가지 않는다.”

이 문서 자체가 기능 구현 승인을 의미하지 않는다.
