# SABA AI RULES

Version: 1.2


==================================================
CRITICAL AI RULE
==================================================

AI MUST NOT be a required dependency of the SABA Core Pipeline.

The Core Pipeline must remain capable of operating without an
AI provider whenever the required source data is available.

Do NOT select, implement, or call an AI provider or model
without explicit user approval.

Do NOT assume that the user will personally pay for an AI API.

Do NOT silently switch from a free AI service to a paid service.

AI failure, missing API credentials, usage limits, cost limits,
or provider outages MUST NOT automatically cause the entire
SABA Core Pipeline to fail when a valid non-AI path exists.

Do NOT fabricate AI-generated information when AI is disabled
or unavailable.

Original source information and AI-generated information MUST
remain distinguishable.

All model-authored user-facing natural-language explanations,
progress messages, reports, and generated prompts MUST be
written in Korean and MUST NOT contain CJK ideographs.


==================================================
1. 목적
==================================================

이 문서는 SABA에서 사용하는 AI 기능,
AI Provider, Model, 비용, 외부 데이터 전송,
API 호출, Secret 관리 및 AI 장애 처리에 대한
공통 하네스 규칙을 정의한다.

AI 관련:

- 설계
- 구현
- 테스트
- 실행
- 후속 프롬프트

에는 이 규칙을 적용한다.


==================================================
2. 최상위 원칙
==================================================

AI는 SABA Core Pipeline의
필수 실행 의존성이 아니다.

SABA는 AI를 사용할 수 없는 상태에서도
가능한 범위의 Core Pipeline을
계속 수행할 수 있도록 설계한다.

AI는 기사 분석과 뉴스레터 품질을 높이는
선택적 보강 기능으로 취급한다.

AI를 사용할 수 없다는 이유로
Source 원본에 존재하지 않는 내용을
임의 생성하거나 추측하여 대체하지 않는다.


==================================================
3. SABA Core Pipeline
==================================================

SABA Core Pipeline은
다음 개념을 기준으로 한다.

뉴스 Source
→ 수집
→ Article 정규화
→ 저장
→ 비AI 기반 처리
→ Newsletter 생성
→ Mail 발송
→ Scheduler


Core Pipeline은 가능한 범위에서
AI Provider와 독립적으로 동작하도록 설계한다.

다음 상황만으로
전체 SABA 실행이 반드시 중단되는 구조를 만들지 않는다.

- AI 기능 비활성
- AI Provider 미선정
- AI Model 미선정
- API Key 없음
- 무료 사용 한도 초과
- 비용 제한
- AI Provider 장애
- AI 요청 실패

단,
AI 없이 수행할 수 없는 기능을
거짓 데이터로 채우지 않는다.


==================================================
4. 현재 AI 승인 상태
==================================================

현재 승인 상태:

- AI Provider: 미확정
- AI Model: 미확정
- 유료 AI API 사용: 미승인
- 개인 비용 부담: 전제로 하지 않음
- 무료 AI API: 우선 검토 대상
- 회사 데이터 외부 전송 적합성: 확인 필요
- 실제 AI API 구현: 미승인
- 실제 AI API 호출: 미승인


과거 프롬프트,
과거 설계 문서,
과거 제안에
특정 Provider 또는 Model이 적혀 있다는 이유만으로
현재 승인된 것으로 간주하지 않는다.

사용자의 최신 명시적 승인 상태를 우선한다.


==================================================
5. AI 선택 기능
==================================================

AI는 다음과 같은 보강 기능에 사용할 수 있다.

- 기사 의미 기반 분류
- 중요도 판단
- 기사 선별 보조
- 기사 요약
- 핵심 내용 추출
- 태그 생성
- Newsletter용 제목 보강
- Hook 생성
- 왜 봐야 하는지 작성
- 시사점 초안
- 관련 부서 판단
- 유사 사건 판단 보조

이 목록은
사용 가능한 후보 기능을 의미한다.

목록에 존재한다는 이유만으로
현재 구현 또는 사용이 승인된 것은 아니다.

각 기능은 해당 구현 단계의
사용자 승인 범위에 따라 적용한다.


==================================================
6. AI 미사용 경로
==================================================

AI를 사용하지 않는 경우에도
가능한 Core Pipeline을 계속 수행한다.

사용 가능한 원본 정보 예:

- Source
- 원본 제목
- URL
- 발행일
- RSS 제공 설명
- RSS 제공 요약
- 공식 API Metadata
- 승인된 수집 과정에서 확보한 정보


비AI 처리는
명시적이고 검증 가능한 규칙만 사용한다.

예:

- 날짜
- Source Metadata
- Feed Category
- 승인된 Keyword 규칙
- Article ID
- URL
- 발행 시각
- 승인된 우선순위


비AI 규칙만으로
기사 의미를 확정할 수 없다면
추측하지 않는다.

필요한 경우:

- 미분류
- 검토 필요
- 분석 없음

등의 명시적 상태를 사용할 수 있다.

정확한 상태명과 Schema 변경은
실제 구현 단계에서 검토하고
필요한 경우 사용자 승인을 받는다.


==================================================
7. AI 결과와 원본 정보 분리
==================================================

Source 원본 정보와
AI 생성 정보를 명확하게 구분한다.

AI 분석이 존재하지 않는 경우
AI가 생성한 것처럼 보이는 다음 정보를
임의로 만들지 않는다.

- 요약
- 중요도
- 시사점
- 관련 부서
- 업무 연결
- Hook
- 왜 봐야 하는지
- 의미 기반 Category

Source가 직접 제공한
Summary 또는 Description은
AI Summary와 구분한다.


==================================================
8. AI 장애 격리
==================================================

AI 계층은 가능한 범위에서
Core Pipeline과 분리한다.

개념적 처리:

Article
→ AI 사용 가능 여부 확인


AI 사용 가능:

→ AI 분석
→ 분석 결과 검증
→ Newsletter 보강


AI 사용 불가:

→ AI 분석 생략
→ Source 원본 정보 및 승인된 비AI 규칙 사용
→ Core Pipeline 계속


AI 전용 필드가 존재하지 않는다는 이유만으로
Newsletter 전체 생성이 반드시 실패하도록
설계하지 않는다.

AI 데이터가 없을 때의
실제 Newsletter 표시 방식은
Newsletter 구현 단계에서 결정한다.


==================================================
9. Provider 및 Model 결정
==================================================

Provider 또는 Model을 결정하기 전에
최소 다음을 확인한다.

- 무료 사용 가능 여부
- 무료 사용 한도
- 무료 초과 시 동작
- 유료 전환 조건
- 입력 비용
- 출력 비용
- 요청 제한
- Rate Limit
- Structured Output 지원
- 필요한 API 기능
- 한국어 처리 가능성
- 데이터 이용 정책
- 회사 데이터 처리 적합성
- 상업적 사용 조건
- 운영 안정성
- Python 연동 난이도
- Secret 관리 방법


선택이 필요한 경우 사용자에게 다음을 제시한다.

- 가능한 방법
- 장점
- 단점
- 비용
- 데이터 처리 조건
- 추천 방법
- 추천 이유


사용자 승인 전
Provider와 Model을 확정하지 않는다.


==================================================
10. 비용 원칙
==================================================

현재 SABA MVP는
사용자의 개인 비용 발생을
기본 전제로 하지 않는다.

사용자의 명시적 승인 없이:

- 유료 API 호출
- 유료 요금제 활성화
- 결제 수단 등록을 전제로 한 구현
- 자동 유료 전환

을 하지 않는다.


무료 API를 사용하는 경우에도:

- 무료 한도
- 호출 한도
- Token 한도
- 무료 초과 시 동작

을 확인한다.


무료 한도를 초과했을 때
자동으로 유료 호출로 전환하지 않는다.

비용을 확인할 수 없다면
무료라고 추정하지 않는다.


==================================================
11. 무료 AI API 원칙
==================================================

무료라는 이유만으로
Provider 또는 Model을 자동 승인하지 않는다.

최소 다음을 확인한다.

- 무료 호출량
- 무료 Token 한도
- Rate Limit
- 무료 정책 유지 조건
- 무료 초과 시 동작
- 입력 데이터 이용 정책
- 학습 또는 제품 개선 사용 여부
- 회사 데이터 처리 적합성
- 상업적 사용 조건
- 운영 환경 사용 가능 여부

회사 데이터 처리에 적합하지 않다면
무료라는 이유만으로 선택하지 않는다.


==================================================
12. 실제 AI API 호출
==================================================

실제 외부 AI API 호출은
다음이 모두 확인된 이후에만 허용한다.

- Provider 승인
- Model 승인
- 비용 정책 승인
- 데이터 전송 범위 승인
- Secret 준비
- 실제 호출 범위 승인


하나라도 미확정이면
실제 API 호출을 하지 않는다.

Mock 및 Fixture 테스트는
실제 API 승인 없이 수행할 수 있다.

Mock 성공을
실제 API 연결 성공으로 표현하지 않는다.


==================================================
13. 회사 데이터 및 외부 전송
==================================================

외부 AI에 전송하는 데이터는
필요한 최소 범위로 제한한다.

다음을 필요 없이 전송하지 않는다.

- 회사 내부정보
- 개인정보
- 인증정보
- Secret
- 전체 DB
- 전체 Article JSON
- 선택되지 않은 기사 원문
- 기존 분석 결과
- 불필요한 Metadata


Provider가 입력 데이터를
학습 또는 제품 개선에 사용할 수 있다면
회사 데이터 사용 적합성을 별도로 검토한다.

정책 판단이 필요하면
사용자에게 보고하고 승인을 기다린다.


==================================================
14. Secret 관리
==================================================

다음을 Source Code에 작성하지 않는다.

- API Key
- Access Token
- Refresh Token
- Client Secret
- Password


환경변수 또는
승인된 Secret 관리 방식을 사용한다.

실제 Secret을:

- 로그
- 오류 메시지
- 테스트 Fixture
- Git
- 문서
- 대화

에 출력하지 않는다.


.env를 사용할 경우
Git에 Commit하지 않는다.

.env.example에는
실제 Secret 값을 넣지 않는다.


==================================================
15. Provider 및 Model 변경
==================================================

Provider 또는 Model 변경을
단순 코드 변경으로 처리하지 않는다.

변경 전에 최소 다음 영향을 확인한다.

- 분석 품질
- 비용
- Schema 호환성
- Structured Output
- Token 제한
- 테스트
- 데이터 정책
- Rate Limit
- 운영 안정성

사용자 승인 후 변경한다.


==================================================
16. 테스트
==================================================

AI 관련 구현은
harness/TESTING_RULES.md를 함께 적용한다.

최소 다음을 구분한다.

- Unit Test
- Mock
- Fixture
- 실제 API 연결
- 실제 뉴스 분석
- 사람 품질 검토

각 결과를 서로 대체하지 않는다.


AI 선택 기능이 구현되는 경우
가능한 범위에서 다음 경로를 각각 검증한다.

1. AI 사용 경로
2. AI 미사용 경로
3. AI 실패 경로


AI 미사용 경로는
실제 외부 AI Network 요청 없이
동작해야 한다.

AI 장애가 Core Pipeline 전체 실패로
불필요하게 전파되지 않는지 확인한다.


==================================================
17. Newsletter와 AI
==================================================

Newsletter Template은
AI 전용 데이터가 없다는 이유만으로
전체 생성이 반드시 실패하도록 설계하지 않는다.

AI 분석이 없는 경우
Source 원본 정보와
승인된 비AI 데이터만 사용한다.

AI 결과가 없는 필드를
임의의 AI 결과로 채우지 않는다.


AI가 없는 경우의:

- Section 표시 여부
- 미분석 표시 방식
- 빈 Field 처리
- 기본 Newsletter 구조

는 Newsletter 구현 단계에서
사용자와 확인 후 결정한다.


==================================================
18. 저작권 및 Source 원문
==================================================

AI가 없다는 이유로
기사 전체 본문을 Newsletter에 복사하지 않는다.

Source별로 다음을 확인한다.

- RSS 제공 범위
- 공식 API 제공 범위
- 이용 조건
- 본문 수집 허용 여부


Newsletter에서는 가능한 범위에서:

- 제목
- Source
- 날짜
- 허용된 Summary 또는 Description
- 기사 Link

를 활용한다.

기사 전체 본문 재배포를
기본 동작으로 가정하지 않는다.

Web Crawling이 필요한 Source는
별도 검토 및 사용자 승인 후 구현한다.


==================================================
19. 프롬프트 규칙
==================================================

AI 관련 단계 프롬프트는
현재 AI 승인 상태를 먼저 확인한다.

미확정 상태를
승인된 값으로 바꾸지 않는다.

다음은 사용자 승인 근거가 있을 때만
확정할 수 있다.

- Provider
- Model
- 유료 API 사용
- 실제 API 호출
- 회사 데이터 외부 전송


AI 관련 프롬프트는
harness/rules/PROMPT_VALIDATION.md의
최종 출력 게이트를 통과해야 한다.


==================================================
20. 현재 상태 변경
==================================================

이 문서의 현재 승인 상태는
사용자의 최신 결정에 따라 변경할 수 있다.

변경할 때 다음을 명확하게 기록한다.

- 무엇이 승인되었는지
- 무엇이 여전히 미확정인지
- 비용 영향
- 데이터 영향
- Core Pipeline 영향


과거 프롬프트에 적힌 값만을 근거로
현재 상태를 자동 변경하지 않는다.


==================================================
21. 규칙 변경
==================================================

이 문서의 규칙을
테스트 또는 구현 편의를 위해
임의로 약화하지 않는다.

규칙 변경이 필요한 경우:

- 변경 이유
- 기존 규칙
- 변경안
- 영향

을 사용자에게 보고한다.

사용자의 최신 명시적 결정과
이 문서가 충돌하면
사용자의 최신 결정을 우선한다.

필요한 문서 갱신을 함께 보고한다.
