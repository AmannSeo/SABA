# SABA PROMPT VALIDATION RULES

Version: 2.3


==================================================
CRITICAL OUTPUT RULE
==================================================

NEVER use CJK ideographs in model-authored user-facing
natural-language output.

This rule applies to ALL model-authored user-facing output,
including:

- progress messages
- status messages
- explanations
- reports
- validation results
- error descriptions
- recommendations
- generated prompts
- corrective prompts
- follow-up prompts

User-facing natural-language output MUST be written in Korean,
except when an exact technical term, code, path, filename,
command, API name, product name, model name, or other exact
identifier must be preserved.

Do NOT use a blacklist of specific CJK characters.

The restriction applies to ALL CJK ideographs in model-authored
user-facing natural-language text.

Before EVERY user-facing output:

1. Scan the complete output for CJK ideographs.
2. If a CJK ideograph exists in model-authored natural-language
   text, do NOT emit the output.
3. Replace it with appropriate Korean text.
4. Scan the complete output again.
5. Re-run all applicable prompt validation rules.

Original source data that must be preserved exactly is exempt.

This exemption does NOT apply to model-authored explanations,
progress messages, reports, or generated prompts.

Violation of this rule is a validation failure.


==================================================
CRITICAL FOLLOW-UP RULE
==================================================

When the current task is complete and the next task is clear
from already approved requirements, generate the COMPLETE
next execution prompt.

Do NOT stop with only:

- a recommendation
- a next-step title
- a short description
- a partial prompt

The generated next prompt MUST be complete enough for the user
to execute directly.

Generating the next prompt does NOT authorize execution of the
next task.

After generating it, STOP and wait for user approval.

If a user decision is required before the next task can be
defined safely, do NOT invent the decision.

Present the available options, advantages, disadvantages,
recommended option, and reason, then STOP.


==================================================
1. 목적
==================================================

이 문서는 SABA 프로젝트에서 작성되는:

- 실행 프롬프트
- 보완 프롬프트
- 수정 프롬프트
- 후속 프롬프트

를 검증하기 위한 공통 하네스 규칙이다.

모든 프롬프트는 사용자에게 제공하기 전에
이 문서의 검증 절차를 통과해야 한다.

프롬프트에 단순히
"검증한다"라는 문장을 작성하는 것으로
검증을 완료한 것으로 처리하지 않는다.

실제 최종 출력 내용을 검사한다.

문제가 발견되면 수정하고
전체 검증을 처음부터 다시 수행한다.

모든 필수 검증을 통과한 경우에만
최종 프롬프트로 제공한다.


==================================================
P01. 한국어 출력 및 한자 문자 사용 금지
==================================================

Codex가 직접 작성하여 사용자에게 보여주는
자연어는 한국어를 기본으로 한다.

모델이 직접 작성한 사용자 표시용 자연어에는
한자 문자를 사용하지 않는다.

특정 한자 목록만 검사하지 않는다.

한자 문자 전체를 검사 대상으로 한다.


적용 대상에는 최소 다음이 포함된다.

- 진행 상태
- 현재 작업
- 완료 작업
- 남은 작업
- 작업 설명
- 결과 보고
- 오류 설명
- 테스트 결과
- 검증 결과
- 선택지
- 장점
- 단점
- 추천 방법
- 추천 이유
- 실행 프롬프트
- 보완 프롬프트
- 수정 프롬프트
- 후속 프롬프트
- SABA 전체 개발 상태
- 최종 결과 보고


모델이 작성한 사용자 표시용 자연어에서
한자 문자가 하나라도 발견되면
P01 실패로 처리한다.


--------------------------------------------------
P01-1. 전체 문자 검사
--------------------------------------------------

특정 문자만 금지하는
블랙리스트 방식으로 제한하지 않는다.

최종 사용자 출력 전체를 대상으로
한자 문자 포함 여부를 검사한다.

한자 문자 영역 전체를 검사 대상으로 한다.

발견된 한자가
모델이 작성한 자연어에 존재한다면
한국어 표현으로 수정한다.


--------------------------------------------------
P01-2. 원본 데이터 보호 예외
--------------------------------------------------

원본 자체를 정확하게 보존해야 하는 데이터는
임의 수정하지 않는다.

예:

- 사용자 제공 원문
- 외부 자료 원문
- 공식 Source 명칭
- 파일 내부 원문
- 코드
- 테스트 Fixture
- URL
- 파일명
- 경로
- API Response 원문
- 검증 대상 원본 데이터

원본에 한자가 포함되어 있다는 이유로
원본 데이터를 변경하지 않는다.

단,
해당 원본을 설명하는
모델 작성 자연어에는
한자를 사용하지 않는다.


--------------------------------------------------
P01-3. 기술 표현
--------------------------------------------------

다음과 같이 정확한 표현을 유지해야 하는
기술 요소는 허용한다.

- 파일명
- 폴더명
- 경로
- 명령어
- 코드
- 클래스명
- 함수명
- 변수명
- API
- CLI
- JSON
- HTTP
- SQL
- Python
- Git
- SQLite
- 제품명
- 서비스명
- 모델명
- 공식 고유명사

기술 요소의 정확성을 유지하기 위한 예외를
일반적인 자연어 설명에 확대 적용하지 않는다.


--------------------------------------------------
P01-4. 진행 상태
--------------------------------------------------

현재 프롬프트 진행 상태도
P01 검증 대상이다.

진행 상태를 출력하기 직전
한자 문자 포함 여부를 검사한다.

다음 항목을 포함한 모델 작성 설명에는
한자를 사용하지 않는다.

- 현재 작업
- 완료
- 진행률
- 현재 상태
- 완료된 주요 작업
- 남은 주요 작업


--------------------------------------------------
P01-5. 최종 출력 검사
--------------------------------------------------

사용자에게 내용을 출력하기 직전에
최종 출력 전체를 검사한다.

한자가 발견되면:

1. 원본 보존 대상인지 확인한다.
2. 원본 보존 대상이 아니라면 한국어로 수정한다.
3. 전체 출력에서 한자를 다시 검사한다.
4. 다른 검증 규칙 위반 여부를 다시 검사한다.
5. P01~P12 전체 검증을 다시 수행한다.

일부 문장만 수정하고
해당 문장만 다시 검사하지 않는다.


==================================================
P02. 사용자 승인 추적
==================================================

프롬프트의 정책과 작업이
실제로 사용자가 승인한 내용인지 확인한다.

과거의:

- 제안
- 추천
- 예시
- 검토안
- 향후 계획

을 승인된 요구사항으로 변경하지 않는다.

특히 다음은 승인 여부를 확인한다.

- 외부 API
- 유료 서비스
- AI Provider
- AI Model
- 회사 데이터 외부 전송
- Mail 발송
- Scheduler
- Admin UI
- Server
- Cloud
- 운영 DB 변경
- 보호 원본 변경

승인 여부가 불분명하면
임의로 확정하지 않는다.

사용자의 최신 명시적 결정을 우선한다.


==================================================
P03. 현재 상태 검증
==================================================

프롬프트를 작성하기 전에
현재 Repository 상태와
실제 개발 상태를 확인한다.

최소 확인 대상:

- PROJECT_RULES.md
- DEVELOPMENT_STATUS.md
- harness/ 아래의 모든 규칙 파일
- 현재 경로에 적용되는 AGENTS.md
- 실제 Source Code
- Test
- Fixture
- Git 상태
- 완료된 기능
- 미구현 기능

과거 테스트 결과를
현재 결과처럼 사용하지 않는다.

이전 프롬프트가 일부 실행된 경우
현재 Git Worktree를 먼저 확인한다.

이미 완료된 유효한 작업을
단계 번호만을 이유로 다시 수행하지 않는다.


==================================================
P04. 허용 범위와 제외 범위 정합성
==================================================

다음 사이에 모순이 없는지 확인한다.

- 작업 목표
- 허용 작업
- 변경 가능 범위
- 제외 작업
- 완료 조건

한 영역에서 금지한 작업을
다른 영역에서 요구하지 않는다.

현재 단계에서 제외된 기능을
완료 조건에 포함하지 않는다.


==================================================
P05. 원본 및 사용자 데이터 보호
==================================================

PROJECT_RULES.md의 보호 규칙을 적용한다.

사용자 승인 없이 다음을 수행하도록
요구하지 않는다.

- 보호 파일 수정
- 보호 파일 이동
- 보호 파일 이름 변경
- 보호 파일 삭제
- 사용자 DB 초기화
- 사용자 DB 삭제
- 사용자 DB Migration
- 사용자 변경 reset
- 사용자 변경 revert
- 사용자 변경 delete
- 사용자 변경 overwrite
- Secret 출력

테스트에는 가능한 범위에서
임시 파일과 임시 DB를 사용한다.

이전 프롬프트가 일부 실행된 경우에도
기존 변경을 무조건 되돌리지 않는다.


==================================================
P06. 기존 구현 재사용 및 구현 가능성
==================================================

이미 존재하는 기능을 확인한다.

단계 번호만을 이유로
완료된 기능을 다시 구현하지 않는다.

기존:

- Schema
- Validation
- Storage
- CLI
- Utility
- Fixture
- Test

를 재사용할 수 있는지 확인한다.

현재 MVP에 필요하지 않은
불필요한 구조와 의존성을 추가하지 않는다.

현재 프로젝트 환경에서
실제로 수행 가능한 작업인지 확인한다.


==================================================
P07. 검증 가능한 완료 조건
==================================================

완료 조건은 실제 결과로
검증 가능해야 한다.

가능한 경우 다음을 확인한다.

- 실행 명령
- 테스트 결과
- 테스트 개수
- 종료 코드
- 생성 파일
- 변경 파일
- DB 영향
- Network 요청 여부
- 보호 파일 Hash
- Git 상태

검증할 수 없는 추상적인 조건만으로
완료를 선언하지 않는다.


==================================================
P08. 검증 한계 구분
==================================================

다음을 명확하게 구분한다.

- Unit Test
- Mock
- Fixture
- CLI 검증
- 실제 외부 연결
- 실제 운영 환경
- 사람 품질 검토

Mock 성공을
실제 외부 연결 성공이라고 표현하지 않는다.

합성 데이터 검증을
실제 뉴스 품질 검증이라고 표현하지 않는다.

실행하지 않은 검증을
성공했다고 표현하지 않는다.


==================================================
P09. 오류 및 로그 안전성
==================================================

오류를 숨기지 않는다.

필수 검증 실패를
성공으로 처리하지 않는다.

로그나 오류에 다음을 노출하지 않는다.

- API Key
- Password
- Token
- Authorization Header
- Secret
- 전체 기사 본문
- 전체 사용자 DB
- 불필요한 전체 API Response

실패 원인과 영향을 구분해서 보고한다.


==================================================
P10. 상태 관리
==================================================

DEVELOPMENT_STATUS.md를
SABA의 공식 개발 상태 문서로 사용한다.

중복되는 별도의:

- Progress 파일
- Stage Status 파일
- Roadmap 상태 파일

을 만들지 않는다.

현재 프롬프트 진행률을 저장하기 위해
별도 진행률 파일을 만들지 않는다.

DEVELOPMENT_STATUS.md의 기존 구조를
사용자 승인 없이 임의 재설계하지 않는다.


==================================================
P11. 종료 및 후속 프롬프트
==================================================

현재 작업의 종료 조건을 명확하게 한다.

사용자 승인 없이
다음 개발 작업을 실행하지 않는다.


현재 작업이 정상 완료되고
다음 작업이 현재 승인된 요구사항만으로 명확하다면
결과 보고와 함께
다음 실행용 프롬프트 전체를 작성한다.

다음 단계 이름이나
간단한 설명만 제공하고 종료하지 않는다.

사용자가 그대로 입력할 수 있는
완전한 후속 프롬프트를 제공한다.


후속 프롬프트 작성은
후속 작업 실행 승인이 아니다.

후속 프롬프트를 작성한 뒤 멈추고
사용자 확인을 기다린다.


정상 완료 흐름:

현재 작업 완료
→ 검증
→ 결과 보고
→ 다음 작업 판단
→ 후속 프롬프트 전체 작성
→ 후속 프롬프트 검증
→ STOP
→ 사용자 확인


다음 작업을 결정하기 위해
사용자 결정이 필요하다면
임의로 후속 프롬프트를 확정하지 않는다.

다음 내용을 제공한다.

- 가능한 방법
- 장점
- 단점
- 추천 방법
- 추천 이유

그리고 멈춘다.


현재 작업이 실패한 경우:

실패 확인
→ 완료 처리 금지
→ 실패 결과 보고
→ 필요한 경우 보완 프롬프트 전체 작성
→ STOP
→ 사용자 확인


==================================================
P12. 검증 규칙 자체의 적용
==================================================

프롬프트에
검증한다는 문장이 존재한다는 이유만으로
검증 완료로 판단하지 않는다.

실제로 P01~P12를 적용한다.

문제가 발견되면 수정한다.

수정 후 P01~P12 전체를
처음부터 다시 적용한다.

다음과 충돌하는지도 확인한다.

- PROJECT_RULES.md
- DEVELOPMENT_STATUS.md
- harness/ 아래의 다른 규칙
- 사용자의 최신 결정

사용자 결정이 필요한 충돌은
임의 해결하지 않는다.


==================================================
2. 현재 프롬프트 진행 상태
==================================================

실행 프롬프트는 가능한 경우
사용자가 현재 작업 위치를
확인할 수 있도록 구성한다.

여기에서 사용하는 진행률은:

현재 프롬프트 진행률

이다.

SABA 전체 프로젝트 진행률이 아니다.


작업 시작 시
현재 프롬프트의 작업을
검증 가능한 작업 단위로 나눈다.

각 작업 상태:

- 대기
- 진행 중
- 완료
- 실패
- 사용자 확인 필요
- 해당 없음


현재 프롬프트 진행률 계산:

완료된 작업 단위 수
/
전체 적용 작업 단위 수
× 100


"해당 없음"은
전체 적용 작업 수에서 제외한다.

다음 상태는 완료로 계산하지 않는다.

- 진행 중
- 실패
- 사용자 확인 필요

진행률을 추측하지 않는다.


==================================================
3. 현재 프롬프트 진행 상태 출력
==================================================

중간 진행 출력이 가능한 환경에서는
주요 작업 경계에서 다음 형식을 사용한다.

[현재 프롬프트 진행 상태]

현재 작업:
<현재 작업>

완료:
<n> / <전체 적용 작업 수>

진행률:
<n>%

현재 상태:
<진행 중 / 실패 / 사용자 확인 필요>


필요한 경우 다음도 표시한다.

완료된 주요 작업:
- ...

남은 주요 작업:
- ...


이 출력도 P01을 적용한다.

출력 전에
모델 작성 자연어에 한자 문자가 없는지 검사한다.


==================================================
4. 현재 프롬프트 진행률 100% 조건
==================================================

현재 프롬프트 진행률 100%는
모든 필수 작업과 검증이 완료된 경우에만 사용한다.

최소 조건:

- 모든 필수 작업 완료
- 필수 테스트 실행
- 필수 테스트 통과
- 보호 원본 검증 완료
- 결과 검증 완료
- 최종 하네스 검증 완료

테스트나 검증이 남아 있다면
100%로 표시하지 않는다.

실패 작업을 완료로 계산하지 않는다.


==================================================
5. SABA 전체 개발 상태
==================================================

현재 프롬프트 진행률과
SABA 전체 개발 상태를 구분한다.

필요한 경우 다음 형식을 사용한다.

[SABA 전체 개발 상태]

현재 위치:
<현재 개발 위치>

완료 영역:
- ...

진행 중 또는 검토 영역:
- ...

미구현 주요 영역:
- ...

다음 결정 필요 사항:
- ...


현재 전체 개발 범위와
작업별 가중치가 공식 확정되지 않았으므로
SABA 전체 프로젝트에 임의의 퍼센트를 부여하지 않는다.

전체 개발 진행률을 숫자로 추측하지 않는다.


==================================================
6. AI 관련 프롬프트 추가 검증
==================================================

AI 관련 작업에는
harness/AI_RULES.md를 함께 적용한다.

최소 확인:

- AI가 Core Pipeline의 필수 의존성이 아닌지
- Provider 승인 여부
- Model 승인 여부
- 비용 승인 여부
- 개인 비용 발생 여부
- 무료 한도
- 무료 초과 동작
- 회사 데이터 외부 전송 여부
- Secret 관리
- 실제 API 호출 승인 여부

미확정 항목을
프롬프트에서 임의 확정하지 않는다.


==================================================
7. 이전 프롬프트 일부 실행 처리
==================================================

이전 프롬프트가 일부 실행된 상태라면
현재 Repository 상태를 먼저 확인한다.

이미 수행된 작업이:

현재 요구사항과 일치
→ 재사용

일부 일치
→ 기존 작업을 보존하고 필요한 부분만 수정

충돌
→ 충돌 범위를 확인하고 최소 수정

사용자 변경인지 판단 불가
→ 임의 수정하지 않고 보고


사용자 승인 없이 다음을 수행하지 않는다.

- git reset
- git clean
- 사용자 변경 강제 revert
- 사용자 파일 강제 삭제
- 사용자 변경 강제 덮어쓰기


==================================================
8. 최종 프롬프트 출력 게이트
==================================================

모든 실행 프롬프트,
보완 프롬프트,
수정 프롬프트,
후속 프롬프트는
사용자에게 제공하기 직전에 검증한다.

순서:

프롬프트 초안 작성
→ P01~P12 전체 검증
→ harness/ 아래의 모든 적용 규칙 검증
→ 모델 작성 사용자 표시 자연어의 한자 문자 전체 검사
→ 현재 프롬프트 진행 상태 규칙 검증
→ SABA 전체 상태와의 혼동 여부 검증
→ 문제 수정
→ P01~P12 전체 재검증
→ harness/ 전체 적용 규칙 재검증
→ 한자 문자 전체 재검사
→ 진행 상태 규칙 재검증
→ 최종 통과 확인
→ 사용자 출력


수정 사항이 하나라도 발생하면
부분 검사만 하지 않는다.

전체 검증을 처음부터 다시 수행한다.


==================================================
9. 자동 실패 조건
==================================================

다음 중 하나라도 발견되면
최종 검증 실패로 처리한다.

- 모델 작성 사용자 표시용 자연어의 한자 문자
- 깨진 문자
- 인코딩 오류 문자
- 승인되지 않은 기능
- 승인되지 않은 Provider
- 승인되지 않은 Model
- 승인되지 않은 유료 API
- 승인되지 않은 회사 데이터 외부 전송
- Secret 노출
- 보호 원본 변경
- 사용자 DB 손상 가능 작업
- 사용자 변경 강제 삭제
- Mock 결과를 실제 성공으로 표현
- 미실행 작업의 성공 주장
- 필수 테스트 실패 은폐
- 사용자 승인 없는 다음 개발 작업 실행
- 허용 범위와 제외 범위 충돌
- 근거 없는 현재 프롬프트 진행률
- 필수 검증 완료 전 100% 표시
- 현재 프롬프트 진행률을 SABA 전체 진행률로 표현
- 근거 없는 SABA 전체 퍼센트
- 다음 작업이 명확한데 후속 프롬프트 전체 누락


==================================================
10. 수정 후 전체 재검증
==================================================

검증 과정에서 문제를 하나라도 수정하면
기존 검증 결과를 폐기한다.

수정된 전체 내용을 대상으로
검증을 처음부터 다시 수행한다.

순서:

P01
→ P02
→ P03
→ P04
→ P05
→ P06
→ P07
→ P08
→ P09
→ P10
→ P11
→ P12
→ 적용되는 모든 harness 규칙
→ 한자 문자 전체 검사
→ 현재 프롬프트 진행 상태 규칙
→ SABA 전체 상태 구분
→ 최종 출력 게이트

재검증하지 않았다면
최종 검증 완료로 처리하지 않는다.


==================================================
11. 결과 보고
==================================================

실행 프롬프트의 최종 결과에는
작업 성격에 맞는 실제 검증 결과를 보고한다.

가능한 경우:

- 변경 파일
- 실행 명령
- 테스트 개수
- 테스트 성공 여부
- 실패 여부
- 종료 코드
- 보호 파일 검증
- 사용자 DB 영향
- Git 상태
- 현재 프롬프트 최종 진행 상태
- SABA 전체 개발 상태

를 포함한다.

실행하지 않은 결과를
성공했다고 작성하지 않는다.


==================================================
12. 후속 프롬프트 생성
==================================================

현재 작업이 완료되면
다음 개발 작업을 판단한다.

다음 작업이
현재 사용자 승인 내용만으로 명확하다면
다음 실행용 프롬프트 전체를 생성한다.

후속 프롬프트는 요약이나
일부 지시만 제공하지 않는다.

사용자가 그대로 입력할 수 있는
전체 실행 프롬프트를 제공한다.


후속 프롬프트에도 다음을 적용한다.

- PROJECT_RULES.md
- DEVELOPMENT_STATUS.md
- harness/ 아래의 모든 규칙
- 현재 프롬프트 진행 상태
- 사용자 표시 자연어 한자 금지
- 테스트 규칙
- 보호 원본 규칙
- 종료 조건
- 결과 보고
- 다음 후속 프롬프트 생성 또는 사용자 결정 요청
- STOP


후속 프롬프트도
P01~P12 및 모든 적용 하네스 규칙을
통과한 뒤에만 제공한다.


==================================================
13. 다음 작업이 불명확한 경우
==================================================

다음 작업에 사용자 결정이 필요하면
임의로 개발 방향을 확정하지 않는다.

다음을 제공한다.

- 가능한 방법
- 장점
- 단점
- 추천 방법
- 추천 이유

그리고 멈춘다.

사용자 결정 후
결정에 맞는 실행 프롬프트 전체를 작성한다.


==================================================
14. 규칙 변경
==================================================

이 문서를
작업이나 테스트를 통과시키기 위해
임의로 약화하지 않는다.

규칙 변경이 필요한 경우:

- 변경 이유
- 기존 규칙
- 변경안
- 영향

을 사용자에게 보고한다.

사용자의 최신 명시적 결정과
이 문서가 충돌하면
사용자의 최신 결정을 우선한다.

필요한 문서 갱신을 함께 보고한다.
