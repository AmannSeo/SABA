# SABA PROMPT VALIDATION RULES

Version: 2.0

## 1. 목적

이 문서는 SABA 프로젝트에서 작성되는 실행 프롬프트,
보완 프롬프트 및 후속 단계 프롬프트의 품질과 안전성을
검증하기 위한 공통 하네스 규칙이다.

프롬프트는 사용자에게 제공하기 전에
반드시 이 문서의 P01~P12를 모두 검증해야 한다.

검증은 단순 확인으로 끝내지 않는다.

문제가 발견되면 수정하고,
수정된 전체 프롬프트를 다시 처음부터 검증한다.

모든 필수 항목이 통과한 경우에만
최종 프롬프트로 제공할 수 있다.


==================================================
P01. 언어 및 문자 무결성
==================================================

프롬프트의 설명 문장은 원칙적으로 한국어로 작성한다.

다음과 같이 기술적으로 필요한 표현은 허용한다.

- 파일명
- 폴더명
- 경로
- 명령어
- 코드
- 클래스명
- 함수명
- 변수명
- API
- CLI
- JSON
- HTTP
- SQL
- Python
- Git
- SQLite
- 제품명
- 서비스명
- 모델명
- 공식 고유명사

다음은 허용하지 않는다.

- 불필요한 한자
- 의미 없이 섞인 외국어 문장
- 깨진 문자
- 인코딩 오류 문자
- 복사 과정에서 유입된 비정상 문자
- 한국어로 충분히 표현할 수 있는데 잘못 삽입된 다른 문자

최종 출력 직전에 전체 프롬프트를 다시 검사한다.

의심되는 문자가 발견되면
허용된 기술 표현 또는 고유명사인지 확인한다.

허용 근거가 없다면 수정한다.

수정 후 P01만 다시 검사하는 것이 아니라
P01~P12 전체 검증을 다시 수행한다.


==================================================
P02. 사용자 승인 추적
==================================================

프롬프트에 포함된 정책과 작업이
사용자가 실제 승인한 내용인지 확인한다.

과거 제안,
추천,
예시,
향후 계획을
승인된 요구사항으로 바꾸지 않는다.

특히 다음 항목은 명시적 승인 여부를 확인한다.

- 외부 API 사용
- 유료 서비스 사용
- AI Provider
- AI Model
- 회사 데이터 외부 전송
- Mail 발송
- Scheduler
- Admin UI
- Server 또는 Cloud
- 운영 DB 변경
- 보호 원본 변경

승인 여부가 불분명하면
임의 확정하지 않는다.


==================================================
P03. 현재 상태 검증
==================================================

프롬프트 작성 전에
현재 실제 개발 상태와 일치하는지 확인한다.

최소 확인 대상:

- DEVELOPMENT_STATUS.md
- 실제 Source Code
- Test
- Fixture
- Git 상태
- 현재 단계에서 완료된 기능
- 현재 미구현 기능

과거 테스트 결과를
현재 테스트 결과처럼 작성하지 않는다.

과거 구현 상태와
현재 Repository 상태가 다르면
현재 실제 상태를 우선한다.


==================================================
P04. 허용 범위와 제외 범위 정합성
==================================================

프롬프트의:

- 목표
- 허용 작업
- 변경 가능 파일
- 제외 작업
- 완료 조건

사이에 모순이 없어야 한다.

한 영역에서는 금지하면서
다른 영역에서는 같은 작업을 요구하지 않는다.

현재 단계에서 제외된 기능을
완료 조건에 포함하지 않는다.


==================================================
P05. 원본 및 사용자 데이터 보호
==================================================

PROJECT_RULES.md에서 정의한
보호 대상과 사용자 데이터를 확인한다.

사용자 승인 없이 다음을 요구하지 않는다.

- 보호 파일 수정
- 보호 파일 이동
- 보호 파일 이름 변경
- 보호 파일 삭제
- 사용자 DB 초기화
- 사용자 DB 테스트 데이터 삽입
- 사용자 변경 reset
- 사용자 변경 revert
- 사용자 Secret 출력

테스트에는 가능한 한
임시 파일과 임시 DB를 사용한다.


==================================================
P06. 기존 구현 재사용 및 구현 가능성
==================================================

이미 존재하는 기능을 확인한다.

단계 번호만을 이유로
완료된 기능을 다시 구현하도록 요구하지 않는다.

기존:

- Schema
- Validation
- Storage
- CLI
- Utility
- Fixture
- Test

를 재사용할 수 있는지 확인한다.

불필요한:

- Framework
- Dependency
- 추상화 계층
- Service Layer
- Registry

를 추가하도록 요구하지 않는다.

현재 프로젝트 환경에서
실제로 수행 가능한 작업인지 확인한다.


==================================================
P07. 검증 가능한 완료 조건
==================================================

완료 조건은 실제 명령이나 결과로
검증할 수 있어야 한다.

가능한 경우 다음을 포함한다.

- 실행 명령
- Test 결과
- 종료 코드
- 생성 또는 변경 파일
- DB 영향
- Network 요청 여부
- 보호 파일 Hash
- Git 상태

검증할 수 없는 추상적인 조건만으로
완료를 선언하지 않는다.


==================================================
P08. 검증 한계 구분
==================================================

다음을 명확하게 구분한다.

- Unit Test
- Mock
- Fixture
- CLI 검증
- 실제 외부 연결
- 실제 운영 환경
- 사람 품질 검토

Mock 성공을
실제 외부 API 성공이라고 표현하지 않는다.

합성 데이터를 이용한 성공을
실제 뉴스 품질 검증이라고 표현하지 않는다.

실행하지 않은 검증을
성공했다고 표현하지 않는다.


==================================================
P09. 오류 및 로그 안전성
==================================================

프롬프트는 오류를 숨기도록 요구해서는 안 된다.

필수 검증 실패 시
다음 단계로 진행하지 않는다.

로그나 오류 출력에 다음이 노출되지 않도록 한다.

- API Key
- Password
- Token
- Authorization Header
- Secret
- 전체 기사 본문
- 전체 사용자 DB 내용
- 불필요한 전체 API Response

실패 원인과 영향을 구분해서 보고하도록 한다.


==================================================
P10. 상태 관리 파일
==================================================

DEVELOPMENT_STATUS.md를
SABA의 공식 개발 상태 문서로 사용한다.

중복되는 별도의:

- Progress 파일
- Stage Status 파일
- Roadmap 상태 파일

을 만들지 않는다.

단계별 실행 프롬프트를
별도 상태 관리 파일로 사용하지 않는다.

DEVELOPMENT_STATUS.md의 기존 구조를
사용자 승인 없이 임의 재설계하지 않는다.


==================================================
P11. 종료 및 후속 단계 범위
==================================================

현재 단계의 종료 조건을 명확하게 작성한다.

사용자 승인 없이
다음 개발 단계를 실행하도록 요구하지 않는다.

후속 단계 프롬프트 작성과
후속 단계 실행을 구분한다.

후속 프롬프트 작성은
실행 승인이 아니다.

현재 단계 성공 시:

현재 단계 완료
→ 결과 보고
→ 후속 프롬프트 작성
→ STOP
→ 사용자 확인

순서를 기본으로 한다.

현재 단계 실패 시:

실패 확인
→ 완료 처리 금지
→ 실패 결과 보고
→ 보완 프롬프트 작성
→ STOP
→ 사용자 확인

순서를 기본으로 한다.


==================================================
P12. 검증 규칙 자체의 적용 확인
==================================================

프롬프트에
"검증한다"라는 문장만 존재한다고 해서
검증 완료로 판단하지 않는다.

실제로 P01~P12를 순서대로 적용한다.

검증 과정에서 문제가 발견되면 수정한다.

수정 후 전체 P01~P12를 다시 적용한다.

검증 규칙 자체가:

- 서로 충돌하지 않는지
- 현재 PROJECT_RULES.md와 충돌하지 않는지
- DEVELOPMENT_STATUS.md와 충돌하지 않는지
- 다른 harness 규칙과 충돌하지 않는지

확인한다.

충돌을 발견했는데
사용자 승인 없이 해결할 수 없다면
임의 결정하지 않고 사용자에게 보고한다.


==================================================
2. AI 관련 프롬프트 추가 검증
==================================================

AI와 관련된 프롬프트라면
harness/ 아래의 AI 관련 규칙을 추가 적용한다.

특히 다음을 검사한다.

- Provider 승인 여부
- Model 승인 여부
- 무료 또는 유료 여부
- 개인 비용 발생 여부
- 무료 한도
- 무료 한도 초과 동작
- 데이터 이용 정책
- 회사 데이터 외부 전송
- Structured Output 지원
- Secret 관리
- 실제 API 호출 승인 여부

AI 관련 규칙에서
미확정으로 정의된 항목을
단계 프롬프트에서 임의로 확정하면 실패다.


==================================================
3. 최종 프롬프트 출력 게이트
==================================================

모든 실행 프롬프트,
보완 프롬프트,
후속 단계 프롬프트는
사용자에게 출력하기 직전에
최종 검증을 수행한다.

반드시 다음 순서를 따른다.

프롬프트 초안 작성

→ P01~P12 전체 검증

→ 현재 작업에 적용되는
  harness/ 아래의 다른 모든 규칙 검증

→ 문제 수정

→ P01~P12 전체 재검증

→ harness/ 전체 규칙 재검증

→ 최종 통과 확인

→ 사용자에게 최종본 출력


수정 사항이 하나라도 발생하면
부분 검증만 하지 않는다.

전체 검증을 처음부터 다시 수행한다.


==================================================
4. 자동 실패 조건
==================================================

다음 중 하나라도 발견되면
최종 프롬프트 검증 실패로 처리한다.

- 불필요한 한자
- 깨진 문자
- 인코딩 오류 문자
- 승인되지 않은 기능 구현
- 승인되지 않은 Provider 확정
- 승인되지 않은 Model 확정
- 승인되지 않은 유료 API 사용
- 비용 정책 미확정 상태의 유료 호출
- 승인되지 않은 회사 데이터 외부 전송
- Secret 노출 요구
- 보호 원본 변경
- 사용자 DB 손상 가능 작업
- 기존 사용자 변경 삭제
- Mock 결과를 실제 연결 성공으로 표현
- 미실행 작업을 성공으로 표현
- 실패한 필수 테스트를 숨김
- 사용자 승인 없는 다음 단계 실행
- 서로 충돌하는 허용 범위와 제외 범위


==================================================
5. 수정 후 재검증
==================================================

검증 중 하나 이상의 문제를 수정했다면
기존 검증 결과를 폐기한다.

수정된 전체 프롬프트를 대상으로:

P01
→ P02
→ P03
→ P04
→ P05
→ P06
→ P07
→ P08
→ P09
→ P10
→ P11
→ P12
→ 적용되는 harness 규칙
→ 최종 출력 게이트

순서로 다시 검증한다.

재검증을 하지 않았다면
최종 검증 완료로 처리하지 않는다.


==================================================
6. 최종 검증 결과
==================================================

프롬프트를 사용자에게 제공할 때
내부적으로 최소 다음 상태를 확인한다.

- P01~P12 전체 검사 완료
- 적용되는 harness 규칙 검사 완료
- 발견 문제 수정 완료
- 수정 후 전체 재검증 완료
- 자동 실패 조건 없음
- 최종 출력 게이트 통과

하나라도 충족되지 않으면
최종본을 제공하지 않는다.


==================================================
7. 규칙 변경
==================================================

이 문서 자체를
단계 실행 중 임의로 약화하지 않는다.

테스트나 프롬프트를 통과시키기 위해
검증 조건을 삭제하거나 완화하지 않는다.

규칙 변경이 필요한 경우:

- 변경 이유
- 기존 규칙
- 변경안
- 영향

을 사용자에게 보고하고
승인된 범위에서만 변경한다.
