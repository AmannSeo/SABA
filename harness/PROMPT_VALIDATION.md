# SABA PROMPT VALIDATION RULES

Version: 3.0


==================================================
CRITICAL INSTRUCTION
==================================================

This file defines the permanent validation framework for SABA
execution instructions, task results, and follow-up prompts.

Do not modify this file merely because a single task produced an
undesirable result.

A rule change is justified only when:

1. the SABA project policy itself has changed;
2. a structural defect exists in this validation framework; or
3. the user explicitly approves a rule change.

Do not patch this file repeatedly for individual prompt failures.

All model-authored user-facing natural-language output MUST be
written in Korean.

Model-authored user-facing natural-language output MUST NOT
contain CJK ideographs.

This applies to progress messages, explanations, reports,
validation results, errors, recommendations, execution prompts,
corrective prompts, and follow-up prompts.

Exact source data, code, commands, paths, filenames, URLs,
official names, API responses, fixtures, and other identifiers
that must be preserved exactly are exempt from transformation.

The exemption does NOT apply to model-authored explanations.

Before emitting user-facing output, validate the complete output.

If validation fails:

1. do not emit the invalid output;
2. correct the problem;
3. discard the previous validation result;
4. validate the complete output again.

Do not rely on the user or another conversation as the normal
quality-control mechanism.

The model executing the task is responsible for validating its
own result and any follow-up prompt it generates.

When a task is complete and the next task is clear, generate and
validate the COMPLETE next execution prompt, then STOP.

Generating a follow-up prompt is NOT permission to execute it.

Never execute the next development task without user approval.


==================================================
1. 목적
==================================================

이 문서는 SABA 프로젝트에서 수행하는 작업의
입력, 실행 범위, 결과, 검증, 후속 작업 사이의
일관성을 유지하기 위한 공통 검증 규칙이다.

검증 대상은 다음과 같다.

- 실행 프롬프트
- 보완 프롬프트
- 수정 프롬프트
- 작업 결과
- 진행 상태
- 오류 보고
- 선택지와 추천
- 후속 프롬프트

이 문서의 목적은
프롬프트 문장 형식만 검사하는 것이 아니다.

다음을 함께 검증한다.

- 현재 실제 프로젝트 상태
- 사용자 승인 범위
- 작업 범위
- 보호 대상
- 테스트 요구사항
- 작업 결과
- 다음 작업과의 연결
- 사용자에게 제공되는 최종 출력

"검증했다"라는 문장을 작성하는 것만으로
검증 완료로 처리하지 않는다.


==================================================
2. 규칙 우선순위와 역할
==================================================

SABA 작업에서는 각 문서의 역할을 구분한다.

PROJECT_RULES.md
- 프로젝트 최상위 원칙
- 보호 대상
- 사용자 승인 원칙
- 프로젝트 공통 제약

DEVELOPMENT_STATUS.md
- 현재 실제 구현 상태
- 완료 영역
- 미구현 영역
- 현재 개발 위치

harness/PROMPT_VALIDATION.md
- 작업 범위 검증
- 결과 검증
- 출력 검증
- 후속 작업 검증

harness/TESTING_RULES.md
- 테스트 작성
- 테스트 실행
- 회귀 검증
- 테스트 결과 보고

harness/AI_RULES.md
- AI 사용 여부
- AI 선택 기능
- Provider와 Model
- 비용
- 외부 데이터 전송
- AI 장애 처리


같은 내용을 여러 규칙 파일에
불필요하게 중복 정의하지 않는다.

충돌이 발생하면
사용자의 최신 명시적 결정을 우선한다.

규칙 문서 사이에 실제 충돌이 확인되면
임의로 한쪽을 무시하지 않고 보고한다.


==================================================
3. 작업 시작 전 상태 확인
==================================================

작업 시작 전에
현재 실제 상태를 확인한다.

최소 확인 대상:

- PROJECT_RULES.md
- DEVELOPMENT_STATUS.md
- harness/ 아래의 모든 규칙 파일
- 현재 작업 경로에 적용되는 AGENTS.md
- 작업과 관련된 Source Code
- 관련 Test
- 관련 Fixture
- Git Branch
- Git Worktree

필요한 파일만 추가로 확인한다.

과거 프롬프트에 기록된 상태보다
현재 Repository 상태를 우선한다.

과거 테스트 결과를
현재 테스트 결과처럼 사용하지 않는다.

이미 완료된 기능을
단계 번호만을 이유로 다시 구현하지 않는다.

이전 작업이 일부 실행된 상태라면
현재 변경 내용을 먼저 확인한다.


==================================================
4. 사용자 승인 상태 검증
==================================================

작업에 포함된 결정이
사용자가 실제 승인한 것인지 확인한다.

다음은 승인과 동일하게 취급하지 않는다.

- 제안
- 추천
- 예시
- 후보
- 검토안
- 향후 계획
- 과거 프롬프트의 가정

특히 다음 항목은
명시적 승인 상태를 확인한다.

- 새로운 외부 Source
- Web Crawling
- 외부 API
- AI Provider
- AI Model
- 유료 서비스
- 실제 AI API 호출
- 회사 데이터 외부 전송
- 실제 Mail 발송
- 운영 수신자
- Scheduler
- Admin UI
- Server
- Cloud
- 운영 DB 변경
- 보호 원본 변경

승인 여부가 불명확하면
임의로 승인된 것으로 처리하지 않는다.

이미 사용자가 결정한 사항을
불필요하게 다시 묻지 않는다.


==================================================
5. 작업 범위 검증
==================================================

작업 시작 전에 다음을 구분한다.

- 이번 작업의 목적
- 허용 작업
- 변경 가능한 파일 또는 영역
- 제외 작업
- 완료 조건
- 사용자 결정이 필요한 항목

이 항목들 사이에 모순이 없어야 한다.

한 영역에서 금지한 작업을
다른 영역에서 요구하지 않는다.

설계 단계라면
승인되지 않은 구현을 진행하지 않는다.

구현 단계라면
승인된 설계를 임의로 다시 설계하지 않는다.

검증 단계라면
검증을 이유로 승인 범위 밖 기능을 추가하지 않는다.


==================================================
6. 기존 구현과 사용자 변경 보호
==================================================

현재 구현을 먼저 확인하고
재사용 가능한 코드를 재사용한다.

다음 기존 요소를 확인한다.

- Schema
- Validation
- Storage
- Collector
- CLI
- Utility
- Fixture
- Test
- Template
- 기타 현재 구현

완료된 기능을
불필요하게 다시 작성하지 않는다.

사용자 승인 없이 다음을 수행하지 않는다.

- git reset
- git clean
- 사용자 변경 강제 revert
- 사용자 파일 삭제
- 사용자 변경 덮어쓰기
- 사용자 DB 초기화
- 사용자 DB 삭제
- 사용자 DB Migration
- 보호 파일 수정
- 보호 파일 이동
- 보호 파일 이름 변경
- 보호 파일 삭제

사용자 변경인지 판단할 수 없다면
임의로 제거하지 않는다.


==================================================
7. 원본 및 데이터 보호
==================================================

PROJECT_RULES.md에 정의된
보호 대상을 준수한다.

보호 원본을
구현 편의를 위해 수정하지 않는다.

변환이 필요한 경우
별도의 작업 파일을 사용한다.

테스트에서는 가능한 범위에서:

- 임시 파일
- 임시 디렉터리
- 임시 DB
- Fixture
- Mock

을 사용한다.

실제 사용자 데이터를
테스트 편의를 위해 초기화하거나 삭제하지 않는다.

Secret을 다음에 기록하지 않는다.

- Source Code
- Fixture
- Log
- Error
- Git
- 문서
- 사용자 표시 결과


==================================================
8. 현재 프롬프트 진행 상태
==================================================

진행률은
현재 실행 중인 프롬프트의 진행 상태만 의미한다.

SABA 전체 프로젝트 진행률과
혼동하지 않는다.

작업 시작 시
현재 프롬프트를 검증 가능한 작업 단위로 나눈다.

상태는 다음 중 하나로 관리한다.

- 대기
- 진행 중
- 완료
- 실패
- 사용자 확인 필요
- 해당 없음


현재 프롬프트 진행률은 다음 기준으로 계산한다.

완료된 작업 단위 수
/
전체 적용 작업 단위 수
× 100


"해당 없음"은
전체 적용 작업 수에서 제외한다.

다음은 완료로 계산하지 않는다.

- 진행 중
- 실패
- 사용자 확인 필요

진행률을 임의로 추측하지 않는다.


==================================================
9. 진행 상태 출력
==================================================

실행 환경에서 중간 상태 출력이 가능하다면
주요 작업 경계에서 진행 상태를 표시한다.

기본 형식:

[현재 프롬프트 진행 상태]

현재 작업:
<현재 작업>

완료:
<n> / <전체 적용 작업 수>

진행률:
<n>%

현재 상태:
<진행 중 / 실패 / 사용자 확인 필요>


필요한 경우 다음을 추가한다.

완료된 주요 작업:
- ...

남은 주요 작업:
- ...


진행 상태 역시
최종 출력 규칙의 적용 대상이다.


==================================================
10. 현재 프롬프트 100% 조건
==================================================

100%는 단순히
코드 작성이나 문서 작성이 끝났다는 의미가 아니다.

현재 프롬프트에서 요구한
모든 필수 작업과 검증이 완료된 경우에만
100%로 표시한다.

적용되는 경우 최소 다음을 확인한다.

- 필수 작업 완료
- 필수 테스트 완료
- 필수 테스트 통과
- 보호 대상 확인
- 결과 검증 완료
- 최종 하네스 검증 완료

필수 검증이 남아 있거나
실패한 작업이 존재하면
100%로 표시하지 않는다.


==================================================
11. SABA 전체 개발 상태
==================================================

현재 프롬프트 진행률과
SABA 전체 개발 상태는 별개다.

필요한 경우 다음 형식으로 표시한다.

[SABA 전체 개발 상태]

현재 위치:
...

완료 영역:
- ...

진행 중 또는 검토 영역:
- ...

미구현 주요 영역:
- ...

다음 결정 필요 사항:
- ...


전체 개발 범위와
각 영역의 가중치가 공식 승인되지 않았다면
SABA 전체 진행률을 퍼센트로 표시하지 않는다.

근거 없는 전체 진행률을 만들지 않는다.


==================================================
12. 구현 결과 검증
==================================================

작업 결과는
현재 프롬프트의 완료 조건과 직접 비교한다.

가능한 경우 다음 증거를 사용한다.

- 실제 변경 파일
- 실제 실행 명령
- 테스트 결과
- 종료 코드
- 생성 결과
- DB 영향
- Network 요청 여부
- 보호 파일 Hash
- Git 상태

실행하지 않은 검증을
실행한 것으로 표현하지 않는다.

확인하지 못한 사항은
확인 완료로 표시하지 않는다.


==================================================
13. 테스트 검증
==================================================

테스트가 필요한 작업에는
harness/TESTING_RULES.md를 적용한다.

다음을 구분한다.

- Unit Test
- Mock
- Fixture
- CLI 검증
- 실제 외부 연결
- 실제 운영 환경
- 사람 품질 검토

Mock 성공을
실제 외부 연결 성공으로 표현하지 않는다.

과거 테스트 결과를
현재 테스트 결과로 표현하지 않는다.

필수 테스트가 실패하면
현재 작업을 완료로 처리하지 않는다.


==================================================
14. AI 관련 검증
==================================================

AI 관련 작업에는
harness/AI_RULES.md를 적용한다.

특히 다음을 확인한다.

- AI가 Core Pipeline의 필수 의존성이 아닌지
- Provider 승인 여부
- Model 승인 여부
- 비용 승인 여부
- 개인 비용 발생 여부
- 무료 한도
- 회사 데이터 외부 전송 여부
- Secret 관리
- 실제 API 호출 승인 여부

미확정 사항을
임의로 확정하지 않는다.


==================================================
15. 오류 및 검증 실패 처리
==================================================

오류를 숨기지 않는다.

필수 검증 실패를
성공으로 처리하지 않는다.

실패가 발생하면 다음을 구분한다.

- 실패한 작업
- 실패 원인
- 영향 범위
- 현재 단계 완료 가능 여부
- 수정 가능 여부
- 사용자 결정 필요 여부

현재 승인 범위 안에서
명백하게 수정 가능한 구현 오류라면
수정하고 다시 검증할 수 있다.

요구사항 변경이나 사용자 결정이 필요하다면
임의 수정하지 않는다.


==================================================
16. 사용자 표시 언어 및 문자
==================================================

모델이 직접 작성하여 사용자에게 보여주는
자연어는 한국어로 작성한다.

모델 작성 사용자 표시용 자연어에는
한자 문자를 사용하지 않는다.

특정 한자 목록을 만들어
일부 문자만 검사하지 않는다.

한자 문자 전체를 검사한다.

적용 대상:

- 진행 상태
- 설명
- 작업 결과
- 오류 보고
- 테스트 결과
- 검증 결과
- 선택지
- 추천
- 실행 프롬프트
- 보완 프롬프트
- 후속 프롬프트


정확한 원본 보존이 필요한 다음 항목은
원문을 변경하지 않는다.

- 사용자 제공 원문
- 외부 Source 원문
- 공식 명칭
- 코드
- 명령어
- URL
- 파일명
- 경로
- Fixture
- API Response
- 검증 대상 원본 데이터

원본 보존 예외는
모델이 작성하는 설명에 적용하지 않는다.


==================================================
17. 결과 보고
==================================================

작업 완료 후
현재 작업 성격에 맞는 결과를 보고한다.

가능한 경우 다음을 포함한다.

- 수행한 작업
- 변경 파일
- 실행 명령
- 테스트 결과
- 종료 코드
- 외부 연결 여부
- 보호 대상 결과
- 사용자 데이터 영향
- Git 상태
- 미확인 사항
- 현재 프롬프트 최종 진행 상태
- SABA 전체 개발 상태
- 사용자 결정 필요 사항

보고 내용은
실제 수행 결과를 기준으로 한다.


==================================================
18. 다음 작업 판단
==================================================

현재 작업이 끝나면
과거 계획만 보고 다음 단계를 선택하지 않는다.

다음을 기준으로 다음 작업을 판단한다.

- 현재 Repository 상태
- 현재 완료된 기능
- 현재 미완료 기능
- 이번 작업 결과
- 테스트 결과
- 발견된 문제
- 사용자 승인 상태
- DEVELOPMENT_STATUS.md
- 다음 작업의 선행 조건

이미 완료된 작업을
후속 프롬프트에서 다시 구현하도록 요구하지 않는다.

실패한 작업을
완료된 것으로 전제하지 않는다.


==================================================
19. 후속 프롬프트 자동 생성
==================================================

현재 작업이 정상 완료되고
다음 작업이 현재 승인 상태만으로 명확하면
완전한 다음 실행 프롬프트를 작성한다.

다음 단계 제목이나
간단한 설명만 제공하고 끝내지 않는다.

사용자가 그대로 실행할 수 있는
전체 프롬프트를 작성한다.

후속 프롬프트에는
작업 성격에 맞게 다음을 반영한다.

- 현재 실제 상태
- 직전 작업 결과
- 승인된 정책
- 미승인 사항
- 재사용 대상
- 허용 범위
- 제외 범위
- 변경 가능 영역
- 보호 대상
- 테스트
- 외부 연결 범위
- 오류 처리
- 결과 보고
- 현재 프롬프트 진행 상태
- SABA 전체 개발 상태 구분
- 적용되는 하네스 규칙
- 종료 조건
- 다음 후속 작업 판단 규칙

후속 프롬프트 생성은
다음 작업 실행 승인이 아니다.


==================================================
20. 후속 프롬프트 자체 검증
==================================================

작성한 후속 프롬프트를
바로 사용자에게 제공하지 않는다.

후속 프롬프트 자체를
새로운 검증 대상으로 취급한다.

최소 다음을 검증한다.

- 현재 Repository 상태와 일치하는가
- 직전 작업 결과를 반영했는가
- 사용자 승인 범위와 일치하는가
- 이미 완료된 작업을 반복하지 않는가
- 허용 범위와 제외 범위가 충돌하지 않는가
- 보호 대상 규칙을 지키는가
- 필요한 테스트가 포함되었는가
- 실행하지 않은 결과를 전제하지 않는가
- 현재 프롬프트 진행 상태를 올바르게 다루는가
- SABA 전체 진행률을 임의 생성하지 않는가
- 다음 작업 실행을 자동 승인하지 않는가
- 사용자 표시 언어 및 문자 규칙을 지키는가
- 해당 작업에 적용되는 다른 하네스 규칙과 충돌하지 않는가
- 작업 종료 후 다시 다음 작업을 판단하도록 되어 있는가

문제가 발견되면 수정한다.

수정 후
후속 프롬프트 전체를 다시 검증한다.

검증을 통과한 후속 프롬프트만
사용자에게 제공한다.


==================================================
21. 사용자 재검수 의존 금지
==================================================

정상적인 작업 흐름에서
사용자가 결과를 다른 대화나
별도의 검수 과정으로 가져가야만
다음 단계로 진행할 수 있는 구조를 만들지 않는다.

기본 흐름:

현재 작업 실행
→ 결과 검증
→ 오류가 있으면 수정 및 재검증
→ 결과 보고
→ 다음 작업 판단
→ 후속 프롬프트 작성
→ 후속 프롬프트 자체 검증
→ 문제가 있으면 수정 및 재검증
→ 검증된 후속 프롬프트 제공
→ STOP
→ 사용자 실행 승인


사용자는 원할 경우
추가 검토를 요청할 수 있다.

그러나 별도 검수를
정상적인 필수 절차로 만들지 않는다.


==================================================
22. 사용자 결정이 필요한 경우
==================================================

다음 작업을 정의하기 위해
사용자 결정이 반드시 필요하면
임의로 결정하지 않는다.

필요한 결정만 묻는다.

다음 내용을 함께 제공한다.

- 결정할 항목
- 가능한 방법
- 장점
- 단점
- 추천 방법
- 추천 이유
- 다음 작업에 미치는 영향

이미 승인된 사항은
다시 묻지 않는다.

사용자 결정이 필요한 상태에서
임의의 후속 구현 프롬프트를 확정하지 않는다.


==================================================
23. 최종 출력 게이트
==================================================

사용자에게 최종 결과를 제공하기 전에
전체 출력을 검증한다.

검증 순서:

현재 실제 상태 확인
→ 사용자 승인 범위 확인
→ 작업 범위 확인
→ 보호 대상 확인
→ 작업 결과 확인
→ 테스트 결과 확인
→ 오류 및 미확인 사항 확인
→ 진행 상태 확인
→ SABA 전체 상태 구분 확인
→ 후속 작업 판단
→ 필요한 경우 후속 프롬프트 작성
→ 후속 프롬프트 자체 검증
→ 사용자 표시 언어 및 문자 검사
→ 모든 적용 하네스 규칙 확인
→ 최종 출력 전체 검증


문제가 발견되면:

문제 수정
→ 이전 검증 결과 폐기
→ 전체 검증 처음부터 재실행


부분 수정 후
일부 항목만 다시 검사하지 않는다.


==================================================
24. 자동 실패 조건
==================================================

다음 중 하나라도 확인되면
최종 검증 실패로 처리한다.

- 사용자 승인 범위 위반
- 승인되지 않은 기능 실행
- 승인되지 않은 외부 연결
- 승인되지 않은 유료 서비스 사용
- 보호 원본 무단 변경
- 사용자 데이터 손상 가능 작업
- Secret 노출
- 기존 사용자 변경 강제 제거
- Mock 결과를 실제 성공으로 표현
- 과거 테스트를 현재 테스트로 표현
- 미실행 검증을 성공으로 표현
- 필수 테스트 실패 은폐
- 허용 범위와 제외 범위 충돌
- 현재 프롬프트 진행률 임의 생성
- 필수 검증 완료 전 100% 표시
- SABA 전체 진행률 임의 생성
- 모델 작성 사용자 표시 자연어의 한자 문자
- 다음 작업이 명확한데 완전한 후속 프롬프트 누락
- 후속 프롬프트 자체 검증 누락
- 직전 작업 결과와 맞지 않는 후속 프롬프트
- 이미 완료된 작업의 불필요한 재구현 요구
- 사용자 재검수를 정상적인 필수 검증 절차로 요구
- 사용자 승인 없이 다음 개발 작업 실행


==================================================
25. 종료 조건
==================================================

현재 작업은 다음 중 하나의 상태로 종료한다.


정상 완료:

작업 완료
→ 필수 검증 완료
→ 결과 보고
→ 다음 작업 판단
→ 다음 작업이 명확하면 전체 후속 프롬프트 작성
→ 후속 프롬프트 자체 검증
→ 사용자 제공
→ STOP


사용자 결정 필요:

현재 가능한 작업 완료
→ 검증
→ 결과 보고
→ 필요한 결정과 선택지 제공
→ STOP


실패:

실패 확인
→ 완료 처리 금지
→ 영향 확인
→ 결과 보고
→ 현재 승인 범위에서 보완 가능하면 보완 프롬프트 작성 및 검증
→ 사용자 제공
→ STOP


어떤 경우에도
사용자 승인 없이 다음 개발 작업을 실행하지 않는다.


==================================================
26. 이 규칙 파일의 변경 기준
==================================================

이 문서는 개별 프롬프트의 작은 문제를 해결하기 위해
반복 수정하는 파일이 아니다.

다음 경우에만 변경을 검토한다.

1. SABA 프로젝트의 상위 정책이 변경된 경우
2. 현재 규칙으로 처리할 수 없는 구조적 결함이 확인된 경우
3. 다른 하네스 규칙과 구조적인 충돌이 확인된 경우
4. 사용자가 명시적으로 규칙 변경을 요청한 경우


단순한:

- 문구 개선
- 특정 출력 실수
- 특정 단계의 예외
- 한 번 발생한 오류

만으로 규칙 파일을 즉시 수정하지 않는다.

먼저 기존 규칙으로 해결 가능한지 확인한다.


규칙 변경이 실제로 필요한 경우
다음을 확인한다.

- 변경 이유
- 기존 규칙으로 해결할 수 없는 이유
- 변경 범위
- 다른 규칙에 미치는 영향
- 기존 프롬프트에 미치는 영향


사용자 승인 없이
규칙을 임의로 약화하지 않는다.
