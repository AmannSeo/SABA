# SABA 관리자 운영 문서

SABA(Security & AI Briefing Automation)를 운영하는 관리자를 위한 문서다.
현재 운영 방법(명령어 기준)과 향후 관리자 UI 도입 계획을 함께 기록한다.
결정 근거는 `harness/rules/DECISIONS.md` 의 D 번호를 따른다.

---

## 1. 전체 흐름

```
RSS 수집 → 같은 사건 묶음·선별 → AI 분석(요약·중요도) → AI 시사점·업무 연결
→ 메일 전용 HTML 생성 → 고정 TEST 수신자 발송
```

| 단계 | 담당 코드 | 저장 위치 |
|---|---|---|
| RSS 수집 | `python -m saba --collect-rss` | `data/saba.db` |
| 보호나라 공지 본문 | `src/saba/notice_body.py` | `data/boho_bodies.json` |
| AI 분석 | `src/saba/openai_adapter.py`, `src/saba/briefing.py` | `data/analysis.db` |
| AI 시사점·업무 연결 | `src/saba/insights.py` | `data/insights.db` |
| 메일 생성 | `src/saba/mail.py`, `templates/newsletter_mail.html` | `output/daily_YYYYMMDD.eml` |
| 발송 | `src/saba/send_mail.py` | (발송 기록은 로그) |
| 매일 실행 | `src/saba/daily.py` | `logs/daily_YYYYMMDD.log` |

`data/`, `logs/`, `output/daily_*.eml` 은 Git 에 포함되지 않는다.

## 2. 자주 쓰는 명령

모든 명령은 프로젝트 폴더에서 프로젝트 Python 으로 실행한다.

```
.venv\Scripts\python.exe -m saba.daily --run          # 오늘 분량 실행 (수집 → 분석 → 메일 → 발송)
.venv\Scripts\python.exe -m saba.daily --run --no-send   # 메일 생성까지만 (발송 없음, D-071)
.venv\Scripts\python.exe -m saba.daily --register     # 작업 스케줄러 등록 명령 확인 (등록하지 않음)
.venv\Scripts\python.exe -m saba.daily --register --apply   # 작업 스케줄러에 실제 등록·갱신 (승인 후)
.venv\Scripts\python.exe -m saba.send_mail            # 발송 드라이런 (접속·발송 없음)
.venv\Scripts\python.exe -m saba.send_mail --send     # 최근 메일 .eml 을 TEST 수신자에게 1회 발송
.venv\Scripts\python.exe -m saba.admin                # 관리 컨트롤 페이지 시작 (브라우저가 열림, 11절)
.venv\Scripts\python.exe -m saba.admin --stop         # 관리 컨트롤 페이지 종료
.venv\Scripts\python.exe -m saba.deploy --backup      # data\·config\ 백업 zip (부서 PC 이전, docs/DEPLOY.md)
```

설치·이전·자동 실행 등록·제거는 `scripts\saba.ps1` 하나로 한다 (D-068, `docs/DEPLOY.md`).

작업 스케줄러 등록 상태 (2026-10-12 등록, D-063): 작업 이름 `SABA_Daily_Briefing`, 평일 08:00 + 최대 5분 지연.

작업 스케줄러 등록 상태 확인 (PowerShell):

```
Get-ScheduledTask -TaskName SABA_Daily_Briefing
```

## 3. 운영 설정 (`config/daily.json`, D-072)

관리 페이지 "예약 발송 설정" 화면에서 바꾸는 것을 기본으로 한다 (검증 → 저장 → 필요하면 작업 스케줄러 재등록 → 변경 기록).

| 항목 | 현재 값 | 설명 |
|---|---|---|
| `mode` | `weekly` | 반복: `daily` 매일, `weekly` 매주, `monthly` 매월, `dates` 특정 날짜 |
| `weekdays` | 월~금 | 매주일 때 요일 (MON~SUN) |
| `month_days` | 없음 | 매월일 때 날짜 (1~31, 그 달에 없는 날짜는 건너뜀) |
| `dates` | 없음 | 특정 날짜 (YYYY-MM-DD) |
| `time` | `08:00` | 발송 시각 (HH:MM) |
| `random_delay_minutes` | `5` | 최대 무작위 지연 0~30분 (0 이면 정각) |
| `max_analysis_calls` | `20` | 하루 AI 분석 신규 호출 상한 (0~50, 한국 날짜별 모든 실행 합계, D-077) |
| `max_insight_calls` | `20` | 하루 AI 시사점 신규 호출 상한 (0~50, 한국 날짜별 모든 실행 합계, D-077) |
| `send` | `true` | 예약 실행 때 발송 여부. `false` 면 메일만 만든다 ("지금 발송" 버튼은 항상 발송) |
| `log_days` | `90` | 실행 로그 보관 일수 (7~3650) |
| `mail_days` | `30` | 메일 파일 보관 일수 (1~3650) |

- 작업 스케줄러는 매일 같은 시각에 프로그램을 깨우고, 예약 날짜인지는 프로그램이 설정으로 판단한다. 예약일이 아니면 로그 없이 바로 끝난다.
- 반복·요일·날짜·시각·지연이 바뀌면 관리 페이지가 작업 스케줄러를 다시 등록한다 (켜짐·꺼짐 상태 유지, 실패하면 설정 원복). 호출 상한·발송 여부·보관 기간은 다음 실행부터 바로 적용된다.
- 변경 기록: `logs/settings_changes.log` (시각, 항목, 이전 값, 새 값, 재등록 여부). 관리 페이지 "실행 이력·로그 → 설정 변경 이력" 에서 본다.
- 파일을 직접 고친 경우에는 `--register --apply` 를 다시 실행해야 시각 변경이 반영된다.

## 4. 실패 처리 원칙 (D-061, D-062)

- 한 단계라도 실패하면 그날은 발송하지 않는다. 재시도하지 않는다.
- RSS Source 하나만 실패해도 발송하지 않는다 (엄격).
- 로그에는 단계, 건수, 오류 종류만 남긴다. 기사 내용과 Secret 은 남기지 않는다.
- 메일 발송 오류는 단계·오류 종류·SMTP 응답 코드·명령 응답 순서만 표시한다.

로그 예시 (`logs/daily_YYYYMMDD.log`):

```
INFO RSS 수집 완료
INFO 메일 생성 완료: daily_20261012.eml · 표시 3건 · 분석 재사용 0 · 신규 4 · 실패 0 · ...
INFO 발송 완료 1회: 받는 사람 1명 · 메시지 ... bytes · 포트 465 SSL/TLS · ...
```

## 6. 수집 Source (관리 화면에서 변경, 11절 RSS Source 관리)

| ID | 이름 | 비고 |
|---|---|---|
| `cert-eu-security-advisories` | CERT-EU | 공식 |
| `boho-security-notice` | KISA 보호나라 | 공식, 국내, 날짜만 제공 |
| `cisa-cybersecurity-advisories` | CISA | 공식 |
| `the-hacker-news` | The Hacker News | 언론 |
| `boannews` | 보안뉴스 | 언론, 국내 |
| `boho-report-guide` | KISA 보호나라 보고서·가이드 | 공식, 국내, 날짜만 제공 |

브리핑 대상 기간은 실행 시각 기준 최근 24시간 (날짜만 제공하는 Source 는 48시간) 이다.
월요일(KST)은 주말 기사를 포함해 48시간을 더한다 (72시간, 날짜만 제공 Source 96시간, D-063).
따라서 실행 날짜마다 메일 내용이 다르다.

선별 상한: Source 당 5건, 국내·해외 섹션 각 10건 → 보안 심층 뉴스는 하루 최대 20건이다.
오늘의 브리핑 분야는 보안 뉴스·테크(Tech)·보안시장 동향만 채워진다
(일정·핫이슈·기업 소식·경제 지표는 분류 기준과 데이터 출처가 아직 없다).

## 7. 메일 (회사 메일: 한비로메일)

- SMTP: 포트 465, SSL/TLS, AUTH PLAIN (자동 인증 방식 선택은 서버 응답 어긋남으로 사용하지 않음, D-050)
- 보낸 사람·받는 사람: 서명 주소 1명으로 고정 (Cc·Bcc 금지)
- 한비로메일 웹메일 제약 (D-057 진단): script·style 블록 제거, 접기·펼치기 불가, 메일 안 이동 링크 불가, 외부 링크만 동작
- 그래서 메일은 780px table 레이아웃, 간략 보기만 표시, 버튼은 기사 원문 링크로 구성한다 (D-054~D-059)

### Secret (환경 변수, Windows 사용자 환경 변수)

| 이름 | 내용 |
|---|---|
| `OPENAI_API_KEY` | OpenAI API Key |
| `SABA_SMTP_HOST` | SMTP 서버명 |
| `SABA_SMTP_USER` | SMTP 아이디 (메일 주소의 @ 앞부분) |
| `SABA_SMTP_PASSWORD` | 웹메일 비밀번호 |

값은 코드·로그·문서·대화·Git 에 기록하지 않는다. 바꾼 뒤에는 실행 프로그램(VS Code, 작업 스케줄러 대상) 을 다시 시작해야 반영된다.

## 8. 알려진 제한과 확인 사항

- 한비로메일 32일 미로그인 시 SMTP 비활성화 안내가 있다. 웹메일에 주기적으로 로그인한다.
- 작업 스케줄러는 이 PC 가 켜져 있어야 실행된다.
- 중요도(긴급·중요·참고) 는 AI 판단이며 구체 등급 기준은 아직 정의되지 않았다.
- 부서별 업무 연결 대상: 경영전략팀, 기술개발연구소, 보안사업팀, STE본부 (STE본부 범위는 D-063 에서 사용자 제공).
- 작업 스케줄러 작업(SABA_Daily_Briefing) 은 사용자가 로그인해 있을 때만 실행된다.

## 9. 관리자 UI 도입 계획 (D-062, 구현은 별도 승인)

### 목적

SABA 의 주요 기능을 터미널 명령어 없이 관리한다.
관리자 UI 는 Core Pipeline 을 새로 구현하지 않고, 기존 Python 기능을 관리·제어한다.

### 기능 후보

**대시보드**
- 시스템 실행 상태, 자동 실행 ON/OFF, 마지막 실행 일시
- 최근 뉴스 수집 건수, AI 처리 성공·실패 건수
- 뉴스레터 생성 결과, 메일 발송 결과

**뉴스 및 AI 분석 관리**
- 수집 기사 목록, Source 별 수집 현황
- AI 분석 결과 조회, 중요도 확인, 관련 부서 확인, 시사점 확인

**뉴스레터 관리**
- HTML 뉴스레터 미리보기, 최근 생성 뉴스레터 조회, TEST 발송 전 내용 확인

**메일 발송 관리**
- TEST 메일 발송, TEST 수신자 확인, 발송 전 확인 절차
- 최근 발송 이력, 발송 성공·실패 확인
- 실제 전사 발송은 별도 승인 및 권한 통제를 적용한다

**스케줄 관리**
- 실행 시간·요일 변경, 자동 실행 ON/OFF
- 스케줄러 등록 상태 확인, 수동 실행
- 설정 저장 및 실제 스케줄러 반영 상태 확인

**로그 및 운영 상태**
- 뉴스 수집·AI 분석·뉴스레터 생성·메일 발송 로그
- 오류 발생 단계 및 원인 종류, 최근 실행 이력

**시스템 설정**
- AI Provider·Model 확인, AI 호출 상한 확인
- 월 AI 사용량 및 예상 비용 확인
- RSS Source 목록 및 상태 확인, 운영 설정 확인

### 원칙

- Secret 값은 관리자 UI 에 노출하지 않는다 (존재 여부만 표시).
- UI 의 모든 실행·발송·설정 변경은 위 명령과 같은 코드 경로를 사용한다.
- 현재 기능과의 대응: 대시보드·로그는 `logs/`, `data/openai_usage.json`, 스케줄은 `config/daily.json`·`--register`, 발송은 `send_mail`.

## 10. 운영 로드맵 (D-065, 순서 변경 D-070)

현재는 본인(고정 TEST 주소) 대상 TEST 운영이다. 추후 본사 전 인원에게 발송한다.
기능과 관리 컨트롤 페이지를 먼저 완성하고, 설치 패키지와 부서 PC 이전은 마지막에 한다 (D-070). 각 단계는 별도 승인 후 진행한다.

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 1. 관리 컨트롤 페이지 1단계 (완료, D-067) | 대시보드, 로그, 메일 미리보기, 기능별 테스트, 자동 실행 ON/OFF, 메일 로고 축소본 | 터미널 없이 상태 확인·테스트 가능, 메일 크기 축소 |
| 2. 기능 완성·테스트·관리 컨트롤 페이지 확장 (현재) | 남은 기능 구현과 품질 개선, 관리 페이지에 수동 실행·실행 시각 변경·수신자·그룹 관리·그룹 개별 발송과 발송 이력·실패 수신자 재발송 (발송 전 승인 화면 없음, D-076·D-077)·관리자 로그인과 권한. 파일럿 발송은 그룹 발송 잠금 해제 별도 승인 후 | 모든 운영 기능을 관리 페이지에서 사용·확인 가능, 파일럿 그룹 정상 운영 |
| 3. 설치·실행·종료·삭제 패키지와 부서 PC 이전 | 패키지 (설치, 실행, 종료, 자동 실행 등록·해제, 데이터 이전, 삭제), 설치 문서, 로그인 없이 실행, 놓친 실행 보완, 기존 PC 작업 해제 | 패키지로 새 PC 설치·실행 가능, 부서 PC 평일 자동 실행 1주 무사고 |
| 4. 본사 전 인원 발송 | 전체 수신자 그룹 발송 (별도 승인) | 회사 IT·보안 정책 확인 완료 |

패키지 초안 (D-068, D-069) 은 보관만 하고 3단계에서 다시 검토한다: `scripts/saba.ps1`, `src/saba/deploy.py`, `scripts/build_exe.ps1`, `scripts/saba_entry.py`, `docs/DEPLOY.md`. 그 전까지 추가 작업은 하지 않는다.

### 전사 발송 전에 확인할 것

- 회사 IT·보안 정책: 자동 발송 허용, 발신 계정 (개인 계정 또는 부서 공용 계정), 수신자 목록 관리 주체
- 한비로메일 제한: 1회 발송 수신자 수, 하루 발송량, 메일 크기 (현재 약 1.4MB, 로고 원본 약 0.9MB → 축소본 적용 예정, D-066)
- 발송 방식: 개별 발송 또는 사내 배포 그룹 주소 1개로 발송 (배포 그룹 사용 시 발송량·크기 부담이 작다)
- 수신 거부·의견 회신 처리 방법
- 개인정보: 수신자 목록(이름·메일 주소) 의 보관 위치와 접근 권한

### 관리 컨트롤 페이지 범위 (1·2단계, D-070)

- 발송 이력: `data/send_history.db` (Git 제외). 회차 (번호, 시각, 실행 주체, 대상, 결과별 인원, 메일 파일과 그 해시, 재발송이면 원회차) 와 수신자별 결과. 주소는 관리 화면 "실행 이력·뉴스레터 → 발송 이력" 에서만 보이고 로그에는 인원만 남는다. TEST 주소 발송도 기록한다.
- 실패 수신자 재발송 (D-077): 발송 이력에서 회차를 고르면 실패·미시도인 사람만 "다시 보내기" (확인 창). 성공·불명확·이미 재발송 성공한 사람, 지금 중지·삭제됐거나 허용 도메인이 아닌 사람은 제외. 원본 메일 파일을 그대로 다시 쓴다 (새 AI 호출·메일 생성 없음). 파일이 없거나 (보관 기간 만료) 처음과 다르면 중단. 매일 실행과 같은 실행 잠금 안에서 `python -m saba.daily --resend 회차` 로 돌고, 결과는 원회차에 연결된 새 회차로 남는다. 그룹 발송 잠금 중에는 거부하고 TEST 주소로 대신 보내지 않는다. TEST 주소 회차는 대상이 아니다.
- 잠금: `send_mail.GROUP_SEND_APPROVED = False`. 꺼져 있으면 발송 대상 설정 (`config/daily.json` 의 `target_group`) 과 관계없이 고정 TEST 주소 1명에게만 보낸다. 관리 화면에서는 켤 수 없고, 회사 IT·보안 정책 확인과 별도 승인 후 코드에서 바꾼다.

### 화면 디자인 기준 (D-076)

- 강조색 하나 (파랑) 는 메뉴 선택·주요 버튼·선택된 항목에만, 초록·주황·빨강은 성공·주의·실패 같은 상태를 뜻할 때만 쓴다.

### 운영 결함 보완 (D-077)

- 하루 AI 호출 상한: `config/daily.json` 의 하루 상한은 한국 날짜별로 예약·지금·테스트 실행이 함께 쓴다 (분석·시사점 각각). 실제 전송 시도와 전송 전 예약 기록을 소비로 센다 (실패·응답 유실·비정상 종료 포함). 저장된 결과 재사용·키 없음·전송 전 거부는 세지 않는다. purpose 없는 예전 기록은 분석으로 센다. 같은 날 상한을 바꾸면 그날 이미 쓴 만큼을 뺀 나머지만 쓴다. 월 $3 상한은 따로 함께 적용된다.
- 메일 파일 이름: `daily_YYYYMMDD_HHMM.eml`, 같은 분에 다시 실행하면 `-2`, `-3` 을 붙여 새 파일로 저장한다 (덮어쓰지 않음). 저장에 실패하면 보내지 않는다.
- 실행 결과 표시: 일부 실패 중 성공이 1명 이상이면 "부분 발송", 성공이 0명이면 "실패" (받았는지 불명확한 사람이 있으면 그렇게 표시). 보낸 뒤 발송 이력 저장이 실패하면 로그에 "발송 여부 불명확 (발송 이력·받은 편지함 확인)" 으로 남는다.
- TEST 주소 발송도 발송 이력 회차를 먼저 만들고 "전송 중" 을 기록한 뒤에만 보낸다. 재발송 대상은 재발송의 재발송까지 모두 살펴 이미 받은 사람을 다시 고르지 않는다.

## 12. 사용자 피드백 작업 1 (2026-10-13)

작업 1~5는 모두 운영 로드맵 2단계(D-070) 안의 순서다. 작업 5(로그인·권한)까지 완료하기 전에 로드맵 3단계 패키지·부서 PC 이전을 시작하지 않는다.

### 관리 UI (F1~F5)

- 관리 화면의 모든 표에 공통 테두리·구분선·셀 간격·세로 중앙 정렬을 적용했다.
- 표 안 메일·로그·수신자별 결과·파일 링크도 기능 버튼과 같은 `btn` 모양이며 링크 동작은 유지한다. 메뉴·탭·본문의 일반 링크는 각각의 의미를 유지한다.
- 예약 발송 스케줄러가 꺼지면 예약 관련 표 대신 "예약 발송 꺼져 있습니다"를 표시한다. 상태 조회 실패는 꺼짐으로 단정하지 않고 "확인 불가"로 표시한다. 스케줄러 켜짐과 `send=false`(메일 생성만)는 다르다.

- 부분 발송·불명확·생성만·실패·파일 없음은 구분한다. 불명확한 실행에는 전체 실행을 다시 권하지 않고 발송 이력·받은 편지함 확인을 안내한다.

### RSS 신뢰성 읽기 분석 (F10)

기준 실행: `2026-10-13T08:03:27+09:00` 자동 실행, 메일 생성 `2026-10-13T08:04:32+09:00`, `daily_20261013_0803.eml`.
운영 DB·로그·본문 캐시·기존 메일을 읽기 전용으로 읽었다. 실제 RSS·OpenAI·SMTP 접속이나 재생성은 하지 않았다.

현재 DB·현재 Source 설정으로 과거 실행 시각의 선정을 **재계산**했다. 당시 구성·변경 전 원문을 완전히 보존한 실행 스냅샷은 아니므로 과거 단계별 실측으로 주장하지 않는다.

- 현재 누적 기사 308개 중 해당 메일 생성 시각까지 최초 수집된 기사 306개. 이후 최초 수집 2개는 제외.
- 기간 안 157개, 기간 밖 149개. 같은 사건 묶음 후 155개 이슈(관련 기사 2개가 대표와 묶임).
- Source별 최대 5개에서 59개 이슈 제외, 국내·해외 각 최대 10개에서 76개 제외. 분석 대상 대표 이슈 20개.
- 생성 시각 이전 저장된 동일 입력 분석 20개, 대상 밖 11개, 동일 입력 분석 없음 0개. 대상 밖은 게재하지 않는다.
- 재계산한 게재 대표 9개 URL이 저장된 메일에 있고 심층 카드도 9개. 실제 실행 로그의 표시 9개와 일치한다.
- 선정 상한을 **AI 대상 밖 판단 전에** 적용하고, 대상 밖을 제외한 빈자리를 다른 후보로 다시 채우지 않는다. 따라서 Source가 많아도 20개 선별 후 9개만 게재될 수 있다. 보안뉴스 등 기간 안 기사도 지역 상한에서 먼저 제외될 수 있다.
- AI 실패·분석 없음이 항상 기사 제외를 뜻하지 않는다. 가상 데이터 테스트에서 분석 없는 기사는 유지하고 대상 밖만 제외하는 기존 동작을 검증한다.

### 이번 검증의 범위

최종 전체 unittest는 450개 실행 중 449개 통과·1개 Skip, 실패·오류 0개다(97.186초). 실제 OpenAI 테스트는 비활성화했다. 기본 tempfile의 제한 ACL에서 접근 오류가 발생해 테스트 전용 .venv 임시 경로에 상속 ACL로 디렉터리를 만드는 런타임 어댑터를 적용했다. 첫 전체 실행의 진입 스크립트 2건 실패는 환경의 PYTHONIOENCODING 값에 오류 처리 접미사가 포함된 탓이며 utf-8로 맞춘 재실행에서 통과했다. 제품 진입 스크립트와 테스트 assertion은 변경하지 않았다.

시작 기준으로 기록한 운영 자료·보호 원본·템플릿·.gitignore 69개 파일의 해시가 동일하다. 실제 보호 원본은 SAMPLE/Codex/·sign/의 29개 파일이며 과거 보고의 파일 수를 이번 증거로 사용하지 않았다. 이번 화면 검증은 가상 데이터의 HTML/CSS·로컬 HTTP 자동 테스트다. 실제 브라우저 렌더링과 전후 캡처, 실제 RSS·AI·SMTP·발송·스케줄러 조회는 미실행이다. 외부 연결 검증은 네트워크 차단과 별도 승인 경계를 유지했다.
